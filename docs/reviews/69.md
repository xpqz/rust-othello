# Review: Issue 69 — Add D4 symmetry property tests (RED)

Verdict: **request changes**

## Verified

- #68 was merged and closed. This branch is based on the current `main`.
  `cargo fmt --check` and clippy are clean, and `symmetry` passes 6/6.
- `sample()` has no nontrivial symmetry. None of the seven non-identity
  images of `b1` (h2, g8, a7, g1, b8, a2, h7) is in the set, so the equality
  checks in orders, compositions, and inverses cannot pass by coincidence.
- I hand-checked three compositions against the coordinate maps:
  FlipDiag→Rot90 = FlipH, Rot90→FlipDiag = FlipV, FlipH→FlipAnti = Rot90.
  The `apply(&[a, b])` "a then b" convention is used consistently.
- The eight-way distinctness I asked about in #64 is already covered by
  `transform_orientation`, whose eight `b1` images are all different.

## Required

1. **Two of the three commutation boards have no legal moves.** I ran
   `legal_moves` on both hand-built boards in `legal_moves_commute`. Each
   returns **0**. Both sides of the assertion are `transform(0) == 0`, so for
   those boards the test checks nothing. The only real case is the start
   position, and that one is invariant under Rot180 and FlipDiag, so half its
   checks are weak too. The acceptance says "transforms commute with move
   generation", and PLAN.md says to test this on random positions. Generate
   positions with the production `Rng`, for example a few hundred short
   random playouts from `Board::START` using `legal_moves` and `play`.
   Assert commutation at every ply, and assert that a good share of the
   positions have moves. If you keep hand-built boards, assert
   `legal_moves(...) != 0` for each.

2. **Show the tests can fail.** This issue has no RED failure, because the
   transforms already exist, so nothing yet shows these tests catch anything.
   Record a mutation check in `docs/prs/69.md`. For example, swap the `Rot90`
   and `Rot270` arms in `common::transform`, or make `FlipAnti` behave as
   `Rot180`. Note which tests fail, then revert. The second mutation matters
   most, because it is still a valid symmetry, so only orientation and
   composition tests can catch it.

## Minor

3. **Orders are only shown to divide.** Checking `Rot90⁴ = id` shows the
   order divides 4, and an identity implementation also passes it. Add
   `apply(bits, &[Rot90, Rot90]) != bits`, and the same for `Rot270`, so the
   order is exactly 4. Do the same for the order-2 elements:
   `transform(bits, sym) != bits`. #71's wording "orders (not all
   involutions)" asks for this.

4. **Overlap with #71.** #71's scope still says "tests/symmetry.rs tests D4
   orders …, composition, and move-generation commutation". Once this
   merges, update #71 to drop that clause or refer to #69, as was done when
   #69 was rescoped in #64.

5. `assert_eq!(start.count_ones(), 4)` duplicates `movegen::start_moves`.
   Drop it, or use it as the "has moves" guard from item 1.
