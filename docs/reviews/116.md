# Review: Issue 116 — Resumable job journal and parallel match runner (RED)

Verdict: **request changes**

## Verified

- The branch is based on the current `main` (`3df49aa`, with #110 merged).
  The RED commit contains `tools/tests/journal.rs` and the notes.
- The expected failure reproduces:
  `error[E0432]: unresolved import othello_tools::journal`.
- The coverage matches #116's list: the journal round trip and torn line,
  kill and resume, header mismatch, `--jobs` determinism, chunks with
  duplicate, mixed and missing pairs in `report`, voiding, and bad arguments.

## Required

1. **The voiding test depends on the machine's real load, so it fails on a
   busy machine.** After the forced void, `voiding_applies_only_to_time_control`
   resumes an `ab:2:1` (time-controlled) run at `--jobs 1`, and the
   replayed pairs record the *actual* load average. If it exceeds 1, they
   void again, and the final `report` assertion fails with nothing wrong.
   This machine has shown load averages of 6-40 today (6.3 while I checked),
   so it would fail here now. Make the threshold explicit and testable:
   - add `--max-load X` (default: the job count), recorded in the header;
   - the test runs both the original and the resumed command with a large
     `--max-load` (say 1000), and `replace_load` writes a value above it.
   That keeps the forced void deterministic and the replay independent of
   the machine. A test-only environment override would also work, but a
   documented flag is better: #115 needs the threshold pre-registered anyway.
2. **The kill test can pass without interrupting anything.** The test kills
   once at least 3 journal lines exist, but at 3,000 nodes against greedy the
   run is fast. If the process has already exited when `kill()` is called,
   `kill` still succeeds on the unreaped child, and the "resume" re-runs a
   complete journal. The byte-equal report then proves nothing about
   resuming. After `wait()`:
   - assert that the child was killed by the signal (`ExitStatusExt::signal()
     == Some(9)`);
   - assert that the journal then held fewer than the full 12 game lines.
   Without both, the test doesn't show what PLAN requirement 7 asks for.
3. **Half-pair and torn-line replay are tested only at the journal level.**
   `journal_roundtrip_and_torn_line` tests `Journal` directly. Nothing tests
   the match-level rule that "a pair with only one game recorded is replayed
   from scratch" (#116 scope item 2), and the kill test hits it only by
   chance. Add a match-level case:
   - complete a run;
   - truncate the journal so the last pair has one complete game line plus a
     torn partial line;
   - re-run the identical command;
   - require the `report` bytes to equal the reference run's, and the final
     journal to contain each pair's two games exactly once.
4. **Header mismatch covers only the seed.** #116 asks for rejection when the
   seed, node budget, agent or opening file differs. Add the other three: a
   different `--nodes`, a different `--a`, and a different `--openings` file
   (copy the file and change one line, so the content hash differs even if
   the path matched). The opening-file case is what stops a resume from
   silently mixing position sets.

## Nits (non-blocking)

- A smoke assertion that a run prints at least one progress line on stderr
  would cover requirement 6 cheaply (a short run can print on start and at
  the end).
- Clean up temporary files on failure, or name them so leftovers are easy to
  find.

Please address these and re-request RED review.

## Verified

- Item 2: the kill test asserts `signal() == Some(9)` and that fewer than 12
  game lines remain (`< 13` with the header). It can't pass vacuously any

- Item 3: `half_pair_is_replayed_once` leaves pair 5 with game 0 complete and
  a torn `5:1` line (no newline), resumes, and requires a byte-equal report,
  12 game lines and 12 distinct IDs.
- Progress smoke check: done.

## Required

1. **The kill test now contradicts the header-mismatch rule, so it must fail
   against a correct implementation.** `reference` is first written by
   `run(&base)` at `--nodes 3000`. Then `reference_args` re-runs **the same
   path** at `--nodes 20000` and asserts success. Under scope item 1 and
   `header_mismatch_is_rejected`, that second run is a header mismatch and
   has to fail. The only way both tests pass is if the implementation lets
   the node budget through the header check. Drop the first `run(&base)`
   (and its assertion), or give the 20000-node reference its own path.
2. **The new mismatch cases don't check *why* the run failed, and one may
   fail for the wrong reason.**
   - Only the seed case asserts `stderr` contains "header". The nodes, agent
     and openings cases accept any failure. Assert "header" for each.
   - The openings case uses `replacen("d3", "c4", 1)`. The first line
     containing `d3` probably starts with it, and `c4` then changes every
     later square's legality. The run may well be rejected as an illegal
     opening, not a mismatch. Change the line in a way that keeps it legal:
     swap two whole lines, or drop the first line.
   - The case still differs in both path and content, so a header that
     records only the path passes. Round 1 asked for the content-hash case
     ("even if the path matched"). Run with `--openings <copy>`, modify the
     copy in place keeping it legal, re-run the identical command, and
     require a "header" error.

## Nit

- `args.push("--nodes")` after `command()` already passed `--nodes 3000`
  relies on last-flag-wins parsing. `replace_arg`, which you already added,
  states the intent without depending on that.

# Re-review (round 5, GREEN)

Verdict: **request changes**

## Verified

- `./scripts/check.sh` exits 0 (re-run). `journal` is 8/8, and the tools
  are at 1,150 against the raised 1,200 budget. The budget raise is recorded
  as approved by the user, and AGENTS.md, PLAN and the guard agree.
- The behaviour matches the approved tests:
  - The header carries the agents, pairs, seed, nodes, ordering, control,
    `max_load`, the openings path and FNV hash, and the engine commit.
  - Seeds stay `stream(seed, pair, game, side)`, so jobs don't change results.
  - Load voiding is applied only for the `time` control.
  - `report` rejects mixed headers and cross-journal duplicates, and lists
    missing pairs.

## Required

1. **The journal rewrites itself in place, which breaks the requirement this
   issue exists to meet.** PLAN § Interruptible long-running jobs, item 1:
   SIGKILL or power loss must never corrupt or invalidate completed work.
   Three writes truncate the live file and then rewrite it:
   - `Journal::discard` (`journal.rs:120`, `File::create(&self.path)` then
     re-writing every record);
   - the torn-tail repair (`journal.rs:58`, `fs::write(path, valid)`);
   - the empty-header case (`journal.rs:62`).
   A kill between the truncate and the end of the rewrite (and `discard` runs
   on **every** resume that finds a half pair or a void pair) leaves a
   journal missing its header or records, so a day of pairs can be lost on
   the exact path the issue is meant to protect. Either:
   - write the new contents to a sibling temporary file in the same
     directory, flush it, and `fs::rename` it over the journal (atomic on the
     same filesystem); or
   - stop rewriting: append only, let later records supersede earlier ones
     for the same unit (the latest complete pair wins), and keep torn-tail
     handling as "ignore the partial last line, and start the next append on
     a new line".
   Add a test that the rewrite path can't lose completed records. For
   example, after a resume that discards a half pair, every complete pair
   from before the resume is still present. For the rename variant, also
   check that no temporary file is left behind.
2. **(Downgraded to non-blocking; see the addendum below.) The tools grew by
   511 lines against #116's +70-100 estimate, and part of that is
   duplication.** The raised budget covers it, but AGENTS.md's
   "as concise as possible while still understandable" still applies:
   - `Journal::open` builds `Self { .. }` twice, with near-identical
     open-for-append code for the new-file and existing-file paths. Create
     the file with its header if it is missing, then take one common path.
   - Pair completeness is implemented twice: `complete()` in `match` and the
     `match (records.get(..), ..)` with `void` in `report`. Use one function.
   - The `queued` filter,
     `!complete(&saved, pair, "depth", 0.0) || !saved.contains_key(&(pair, 0))`,
     has a redundant second clause, because "depth" never voids, so
     `complete` already checks both games. After the discard step above,
     it's just `!saved.contains_key(&(pair, 0))`, or better, reuse the
     single completeness function.
   - `parse_saved` reads `load` positionally (`parts.get(2)`), but `field` and
     `get` already parse `key value` pairs. Use `get(line, "points")` and
     `get(line, "load")`.
   - The "journal header mismatch" message is built in both `journal.rs` and
     `report_command`.
   State the line count after the pass.

## Notes (non-blocking)

- `Journal::append` returns `Result` but panics with `expect` on I/O errors.
  For a long run, a disk-full error is better returned than panicked; either
  is survivable, but be consistent.
- The header records `engine <git HEAD>`, so any commit to the repository
  (including docs) between sessions makes a resume refuse. That is
  defensible, because it is the issue's own specification, but say it in the
  README's resume section: do not commit to the run's checkout until the run
  finishes, or use a separate worktree for long runs.

## Addendum

Item 2 is **non-blocking**. Tools-crate size is not a gating concern. Take
the clean-ups that make the code clearer, in particular the single
completeness function and the redundant `queued` clause, but don't spend
effort squeezing lines. Only item 1 (atomic journal rewrites) blocks
approval.
