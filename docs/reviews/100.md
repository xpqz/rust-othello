# Review: Issue 100 — Strength ladder on the final position set

Verdict: **request changes**

## Verified

- #99 was merged and closed. This branch is based on the current `main`. No
  production code changed, and the engine is still 992.
- The ladder ran on `openings_final.txt` (hash recorded), seed 100, with
  colours swapped and a pair bootstrap. The four logs are committed with
  configuration lines and per-game IDs and seeds, and the notes say no engine
  change followed inspection.
- Three rungs are valid:
  - vs random, 50 pairs: 100/0/0. The interval is degenerate, as correctly
    noted.
  - vs greedy, 500 pairs: **0.984** [0.976, 0.991], which clears ≥ 95%.
  - vs phase2 at **equal depth 4**, 200 pairs: **0.919** [0.893, 0.943],
    which clears ≥ 65%. Both sides' config lines show depth 4 and no time
    limit. This also serves as the evaluator-only no-regression comparison
    against the only frozen previous configuration, labelled as such, which
    satisfies the "previous frozen configuration" rung given there is no
    `release-N` artifact.

## Required

1. **The "equal time" run isn't equal.** The log's configuration lines:

   ```
   a ab:10:5   (evaluate,    depth 10, time 5, …)
   b phase2:5  (eval_phase2, depth 4,  time 5, …)
   ```

   Both get 5 ms, but phase2 is **capped at depth 4**, while the tuned
   engine may deepen to 10. At 5 ms per move, phase2 will usually finish
   depth 4 early and stop with time unused, while the tuned engine keeps
   deepening. So 0.9725 measures "tuned with more search against phase2 with
   less", not equal time. The scope's ≥ 55% equal-time rung needs **the
   same depth cap and the same time** for both sides (for example both
   capped at 64, so time binds). The `phase2[:<ms>]` grammar can't lift
   phase2's cap today (only `--nodes` does, per #84). So either extend the
   tools rule so a time suffix also lifts every search agent's cap to 64,
   mirroring the `--nodes` rule (a few lines; tools is 632 of 650), or give
   both sides an explicit equal depth with the time suffix. Rerun 400 pairs
   on the final set, with the same seed. This is a rerun of a mis-configured
   comparison, not tuning on the final set, so it doesn't contaminate it,
   but say so in the notes.

## Minor

2. **Say why 5 ms.** The CLI default is 1000 ms per move. A 5 ms equal-time
   result is a valid declared time control, but the README presents the claim
   without the caveat. State that the equal-time rung is at 5 ms per move
   (chosen for run time), and that strength at 1 s isn't measured.

3. **The README undersells the engine.** The opening line says "fixed-depth
   search". The engine now has iterative deepening, time and node limits,
   move ordering, a TT, and WDL/exact endgame solving. #105 owns the README,
   but don't merge an inaccurate one-line summary here; either fix the line
   or leave README changes to #105.

# Re-review (round 2)

Verdict: **approve**

- The equal-time rung is fixed. `effective` now lifts every search agent's
  cap to 64 whenever a time suffix is present (mirroring the `--nodes`
  rule), and still rejects time together with `--nodes`. The rerun's
  configuration lines show `depth 64, time 5` on **both** sides. The result
  is **0.9163** [0.8969, 0.9344] over 400 pairs, which clears ≥ 55% with
  the lower bound above 50%. The old 0.9725 is marked superseded in the
  notes and replaced in the README, and the 5 ms choice and the unmeasured
  1 s default are stated.
- I re-ran `./scripts/check.sh` and it exits 0. The tools release suite
  passes.

## Nits (non-blocking)

- With a time suffix, `ab:<d>:<ms>` now ignores `<d>` (the cap becomes 64).
  That is honest in the logs (`describe` prints depth 64), but the agent
  name then carries a meaningless depth. Document `ab:<d>:<ms>` as
  "time-bound; depth ignored", or accept `ab::<ms>`.
- The README's first line still says "fixed-depth search". Fine to leave to
  #105, as noted in round 1.

Clear to merge. All five ladder rungs pass on the untouched final set.
