# Review: #115 pre-registration (round 1)

Verdict: **changes requested before any validation game.**

The candidate (`pc:100` only), the opponent, the set, the three gates, the
single extension, the pass and fail actions, and the untouched final set
all match the issue and the design's enablement rule.

## Required

1. **The extension as written cannot resume.** The journal header includes
   `pairs`, so re-running the 500 ms match with `--pairs 400` is rejected
   against a 200-pair journal, and a fresh 400-pair run would replay the
   first 200 pairs, which is a second look. Pre-register the mechanism
   now:
   - declare the 500 ms match as `--pairs 400` from the start, and play
     `--pair-range` for the first 200 pairs into one journal;
   - evaluate the gate with `report` on that journal;
   - if and only if the extension triggers, play the remaining pair range
     into a second journal, and evaluate `report` over both.

   Before touching validation, prove this works with a short smoke run on
   `openings_tune.txt` (a few pairs, small node budget): the report of the
   first range alone gives an interval, and the pair-to-opening mapping of
   the first range is the same as in a plain run. Record the smoke
   commands and output in the notes. If `report` cannot summarise a
   partial range, say so and propose the smallest fix.
2. **Write every command in full.** Only the equal-nodes command is given.
   The 500 ms and 3 s commands are described in prose. Pre-register them
   literally, including `--jobs 4 --max-load 4`, the journal and log
   paths, and the pair ranges. The notes also need the exact commands or
   tests for the reported metrics (3 s depth on and off, tries and cuts
   per move, 14-empty solve timing against #108).
3. **Dedicated worktree** (PLAN § Interruptible long-running jobs, item 8),
   pinned at the approved commit, as in #114. Journals stay there. Copy
   the logs back.
4. **Order and stopping rule.** State the order (equal nodes, then 500 ms,
   then 3 s) and what happens on a failed gate. Pre-register that the run
   **stops at the first failed gate**: all three must hold, so later gates
   cannot rescue a failure, and unplayed validation games stay unseen for
   a later attempt.
5. **State the interval.** "Elo lower bound" means the lower end of the
   95% pair-bootstrap interval printed by `match` / `report` (10,000
   resamples). Write that down.

## Notes

- The load average is about 5 now. The equal-time matches must wait for a
  quiet machine. The load rule voids pairs above the job count, but a
  machine that hovers near the limit will stall the run. Tell the user
  when you are ready to start the timed matches.
