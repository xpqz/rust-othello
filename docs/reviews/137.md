## Review: step 3 RED gate, `4cfb02e` (13 November 2026)

### Summary

**Request changes** — add the full-table index-distribution check required
by the issue. Reviewed `4cfb02e0c28fb66815493612c1703c300ba4992d`.

### Major: the spread test does not exercise the actual 22-bit table index

Location: `tests/tt.rs::key_spread` and the corresponding PR notes.

The issue explicitly requires checking the low 22 bits used by the full-size
TT. The new test groups only the low 10 bits and high 10 bits. Neither
constrains bits 10–21. A hash can preserve both histograms and distinct full
keys while leaving those middle index bits constant, concentrating every
position into only 1,024 of the table's 4,194,304 slots. The current test
would miss that serious table-index regression.

Retain the distinct-board/full-key checks and add occupancy measurements
for `key & ((1 << 22) - 1)` (or the equivalent modulo `MAX_ENTRIES`), with
a stated, justified maximum bucket occupancy. Keep the 10-bit checks if
useful, but they do not substitute for this. The average occupancy is only
about 0.048 for 200,000 keys, so a small fixed multiple of that mean is not
a usable integer bound; choose a defensible absolute cap or sparse-occupancy
criterion and document it before GREEN. For example, a cap of six can be
justified under an ideal uniform-hash model rather than choosing a threshold
after seeing the new hash. Include a deliberately clustered-index mutation
to demonstrate that the new criterion detects the gap.

### Accepted coverage and observations

The sample deduplicates actual boards and includes their colour-swapped
twins; full-key uniqueness and nonzero checks are meaningful sampled guards.
The deterministic RNG and whole-playout sampling do not depend on HashSet
iteration order. The existing fixed-depth, exact, TT-domain and tableless
golden contracts remain binding; no node baseline may be adjusted merely
because the hash changes table placement.

Independently evaluated the proposed wrapping-64-bit formula in Python:
the start-position value is indeed `0x33e1ce12151b5cfc`. The outer bijection
also proves injectivity for distinct mover boards with a fixed opponent.
It does not prove a `2^-64` collision probability across arbitrary opponents:
that is a uniform-hash modelling assumption, not a deterministic guarantee.
Qualify the wording accordingly; this is a non-blocking documentation point.

Using the changed hash as the noise evaluator still allows comparison with
independent minimax under that evaluator. A separate frozen noise function
would keep those regression fixtures independent of hash experiments, but
is optional here. Any sample-dependent count changes should be reported as
the notes already promise.

## Re-review: step 3 RED gate, `f36df33` (13 November 2026)

### Summary

**Request changes** — the actual-index coverage is added, but its bucket
counters can overflow and conceal a bad distribution in release builds.
Reviewed `f36df33286ad8b84f063ca11a5ee969cdedc43ef`.

### Major: occupancy counters must not wrap

Location: `tests/tt.rs::occupancy`.

Buckets are `u8` and increment with `+= 1`. A bucket containing 256 keys
panics in debug and wraps to zero in the release test profile. The latter
can make the new predicate accept a distribution violating its cap.

Independently copied the committed `occupancy`/`spread` helpers into a
repo-local optimized Rust probe. Its 200,000 distinct nonzero keys comprise
256 different keys indexing slot zero, plus 199,744 keys occupying separate
slots. The helper reports `(199744, 1)` and `spread` returns true, so the
probe expecting rejection fails. The actual maximum is 256, not one.

Use sufficiently wide counters or saturating counters that preserve failure
above six, and add this concentrated-bucket regression. Verify it rejects
without overflow in both debug and release. The existing widespread-cluster
probe and the full-index criterion are otherwise accepted.

### Minor: correct the probability justification

Location: `spread`'s source comment and the appended PR response.

For n = 200,000 and m = 2^22, the displayed approximation
`m * (n/m)^7 / 7!` is about **4.66e-7**, not below 1e-12. The per-slot
approximation is about 1.11e-13; multiplying across all slots matters.
Cap six remains a reasonable predeclared sampled guard under the uniform
model. Correct the explanation rather than tuning the bound to the new hash.
