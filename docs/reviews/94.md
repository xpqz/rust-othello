# Review: Issue 94 — Mobility scaling and frontier antisymmetry (RED)

Verdict: **request changes**

## Verified

- #93 was merged and closed, which closes Phase 6. This branch is based on
  the current `main`. fmt is clean, and `tests/eval.rs` fails only with
  E0432 for `mobility` and `frontier`.

## Required

1. **The mobility fixture has equal counts, so it will fail in GREEN.** Both
   mobility tests use `play(Board::START, 19)` (after d3). I ran it through
   the library. White to move has **3** moves (c3, c5, e3) and black also has
   **3** (e6, f5, f6). So `assert_ne!(mine, theirs)` in
   `mobility_unequal_counts` fails whatever the implementation does, and
   `mobility_formula`'s fixture gives 0. Pick a position with genuinely
   unequal counts, and assert the count pair explicitly so the fixture can't
   silently degrade.

2. **`mobility_formula` restates the implementation.** It computes
   `(mine - theirs) * 1000 / (mine + theirs + 1)` from the same counts the
   implementation will use, so it can only fail if the code uses a different
   formula. That is the same issue as #62's `terminal_score_range`. Pin a
   **hand-computed number** for a fixed position instead (for example "4 vs 1
   moves → 3000 / 6 = 500"). Add the near-equal, high-count case the scaling
   exists for, such as 11 vs 10 → `1000 / 22 = 45`, not 0.

3. **A `frontier` that always returns 0 passes every frontier test.**
   `frontier_swap` checks only `frontier(START) == 0` and antisymmetry
   under `pass`, and the zero function satisfies both. Pin an absolute value.
   After d3, white (to move) has 1 frontier disc (e5) and black has 4, so
   `frontier = opp − own = 4 − 1 = **3**`. I computed that through the
   library with the standard neighbour-of-empty definition. Add one fixture
   where the side to move has *more* frontier discs, so the sign is pinned
   both ways.

# Re-review (round 3, GREEN)

Verdict: **request changes** (two small)

## Verified

- The tests are unchanged since the RED approval. I re-ran
  `./scripts/check.sh` and it exits 0. The release suite passes, and `eval`
  is 9/9. The engine is 959.
- `mobility` is `(mine − theirs) · 1000 / (mine + theirs + 1)` with
  `MOBILITY_SCALE = 1000`. `frontier` is `opp_frontier − own_frontier` over
  the 8-neighbourhood of empty squares. The wrap masks in `neighbours` are
  correct for all eight directions.

## Required

1. **`evaluate`'s doc comment now documents `MOBILITY_SCALE`.** The new
   code was inserted between the existing `///` block ("Positional table
   plus disc difference … For non-terminal positions; terminals use
   `terminal_score`") and `pub fn evaluate`. So that doc now attaches to
   `pub const MOBILITY_SCALE`, and `evaluate` has none. #73's search relies
   on the non-terminal contract being visible on `evaluate`. Move the new
   items above the doc block, or below `evaluate`.

2. **`neighbours` re-implements `board::shift`.** It hand-codes the eight
   shift-and-mask directions with its own `FILE_A`/`FILE_H`. That is the
   logic `board.rs` already owns in `Dir::ALL` / `shift`, with the masks
   tested exhaustively in #66. Two copies of the edge masks can drift, and a
   wrap bug would then live in only one of them. Use
   `Dir::ALL.iter().fold(0, |acc, &dir| acc | shift(bits, dir))` (one line),
   and drop `FILE_A`, `FILE_H`, and the 10-line body. That is about 12 lines
   back, with the engine at 959 and #95–#97 still to come.
