# Review: Issue 110 — Add ProbCut parameters and threshold arithmetic (RED)

Verdict: **request changes**

## Verified

- The branch is based on the current `main` (`5784e26`). The RED commit
  `707c651` contains `tests/probcut.rs` and the notes, and `b449133` only
  touches the notes.
- The expected failure reproduces:
  `error[E0432]: unresolved import othello::probcut`.
- The hand-computed values are correct. With `t = 150`, `a = 0.900`,
  `b = 30` and `σ = 100`, the margin is `m = 150`, so:
  - `high(500)` = ⌈620000/900⌉ = 689;
  - `high(-100)` = ⌈20000/900⌉ = 23;
  - `low(-400)` = ⌊-580000/900⌋ = -645;
  - `low(100)` = ⌊-80000/900⌋ = -89.
  EdaxStyle: `s = 30 + 16 + 3·4 = 58`, and `58² + 2·58 + 100 = 3580`.
  StageTable gives 140 and 280.
- The constructor rejection cases, the `shallow_depth` table and parity, and
  the domain boundaries match #110 and design § Shallow depth.

## Required

1. **The rounding tests miss the cases most likely to be implemented
   wrongly.** The notes say "including negative numerators", but both `high`
   cases have positive numerators (620 and 20) and both `low` cases negative
   ones. Rust's `/` truncates toward zero, so the classic mistakes go
   untested:
   - `(n + d - 1) / d` for ceil is wrong when `n < 0`;
   - `(n - d + 1) / d` for floor is wrong when `n > 0`.
   Add, with `params()`:
   - **`high` with a negative numerator:** `high(-500, 8, 30)`. The numerator
     is −380, so ⌈−380000/900⌉ = **−422**. The naive form gives −421.
   - **`low` with a positive numerator:** `low(400, 8, 30)`. The numerator is
     220, so ⌊220000/900⌋ = **244**. The naive form gives 245.
   - **Exact division** in each direction, for example a numerator of 900 or
     −900, which must not round by one.
   - **A non-integer margin:** for example `t = 150`, `σ = 33`, so
     `m = ⌈49.5⌉ = 50`. Today `σ = 100` makes `t·σ/100` exact, so the
     margin's ceiling is untested.
2. **The guard tests don't exercise the transformed thresholds.** At
   `β = EVAL_BOUND` and `±INF`, any implementation skips, including one that
   wrongly guards on `β + m − b` before the transform. That is exactly the
   case review finding 6 asked to cover (design § The check (v1),
   "Guards on transformed thresholds"). With `params()`, add:
   - **Untransformed passes, transformed fails:** `high(5700, 8, 30)`. Here
     `β + m − b = 5820 ≤ EVAL_BOUND`, but `H = ⌈5820000/900⌉ = 6467` is
     beyond it, so the result is `None`.
   - **Boundary:** `high(5640, 8, 30) == Some(6400)` (H exactly at the bound is
     probed), and `high(5641, 8, 30) == None`.
   - **The mirror cases for `low`** around `−EVAL_BOUND`.
3. **`extreme_values_do_not_panic` asserts nothing about results.** `let _ =`
   only shows the absence of a panic. With every coefficient saturated, the
   margin is enormous, so every call must return `None`. Assert that. As
   written, an implementation that saturates the margin into a *small* or
   negative value would pass, and that silent wrap is the failure finding 6
   was about.
4. **EdaxStyle cannot represent a real fit with integer coefficients.**
   Edax's own coefficients are fractional (about −0.100, 0.310, −0.578 in the
   linear part; 0.0759, 1.165, 5.417 in the quadratic). An integer `q2 ≥ 1`
   makes `q2·s²` jump in coarse steps, so #111 could never fit this candidate.
   This flaw comes from the design's "integer coefficients" wording, not your
   reading of it, but it has to be settled here because #110 defines the
   type.
   - Use a fixed-point scale, for example thousandths for `a`, `b`, `c` and
     the `q`s, with `s` held at the same scale.
   - Round the final σ **up**: underestimating σ is the dangerous direction
     (design § The σ model).
   - Document the scale in the type's doc comment.
   - Add a test with fractional coefficients against a hand-computed σ.
   - The Linear and StageTable forms stay as they are only if centidisc
     integers are fine enough for them. Say which you chose and why.

## Nits (non-blocking)

- Test that the inclusive bounds are accepted: `t = 50`, `t = 400`,
  `a = 500` and `a = 1500` (the extreme test covers only 400 and 1500).
- The notes say the ranges are capped at 64. Add a rejection test for, say,
  `(3, 65)` and `(0, 65)`.
- StageTable maps 18–23 … 48+. Define and test which bucket serves empties
  below 18, since the extreme test's `(0, 64)` domain would reach them with a
  table model.

Please address these and re-request RED review.

# Re-review (round 3, GREEN)

Verdict: **request changes** (small; conciseness only)

## Verified

- `./scripts/check.sh` exits 0 (re-run). `probcut` is 12/12, the engine is at
  1,140 and the tools at 639. `SearchConfig` and `negamax` are untouched.
- The arithmetic is correct:
  - `ceil_div` truncates toward zero for negative numerators, which is the
    ceiling there, and adds one only for a positive remainder.
  - `div_euclid` with a positive divisor is the floor.
  - The guards compare the transformed `H` and `L`.
  - Margins saturate upward, so they can never shrink.
- The EdaxStyle scale is consistent. With `s` in thousandths:
  - `q2_milli·s²` carries 10⁹;
  - `q1_milli·s·1000` carries 10⁹;
  - `q0_milli·10⁶` carries 10⁹;
  so dividing by 10⁹ with a ceiling is right. The new case checks: `s = 30 + 4 − 4 = 30`, so `σ = 900 + 60 − 3 = 957`. The i128 headroom is ample: the worst case is about 4·10³², against a limit of 1.7·10³⁸.
- StageTable clamps 48 and above to bucket 5, and below 18 to bucket 0.

## Required

1. **Remove the duplicated margin computation.** `high` and `low` compute
   `ceil_div(sigma(..).saturating_mul(t_centi), 100)` identically. Extract a
   private `margin(depth, empties)`.
2. **Use one ceiling helper.** `ceil_div` and `ceil_div_i128` have identical
   bodies. Keep one, either generic over the two integer types or by doing
   the EdaxStyle division in i128 and narrowing before a shared i64 helper.
   Alternatively, express the ceiling as `-((-n).div_euclid(d))`, alongside the
   `div_euclid` floor `low` already uses. That form is safe here: `n` is
   bounded well above `i64::MIN` (β ≥ i32::MIN, margin ≥ 0, b ≤ i32::MAX,
   then ×1000).

Both are small, but they are exactly what AGENTS.md's "as concise as possible
while still understandable" covers.

## Budget (no action needed)

The 142 lines against #110's +20-30 estimate are mostly the design's own
doing: it asked #110 to carry all three σ models, a validating constructor
and the full-grid σ check. That estimate was mine and it was low. #113
already removes the σ variants the fit doesn't choose. In the #113 notes,
record the lines that reclaims, so the epic's total stays visible against
PLAN's revised 50-70 estimate.
