# Review: Issue 89 — Corpus and TT/ordering tests (RED)

Verdict: **request changes**

## Verified

- #88 was merged and closed. This branch is based on the current `main`.
  fmt is clean, and the target fails with the expected E0560 for
  `SearchConfig::ordering`.
- `bench/corpus.txt` has a serialization header and provenance notes, and
  23 positions that include a pass root (the verified b2 / a1|c1 fixture,
  where the opponent's capture wipes `me` out, giving −6400) and two
  terminals.
- `corpus_ordering_nodes` encodes the scope's ≥ 40% ordering cut as
  `ordered ≤ 60% of unordered`.

## Required

1. **`corpus_preload` tests nothing.** It stores entries only under
   `zobrist(board)`, the **root**, and the root is never probed:
   `search_inner`'s root loop calls `negamax` on the children, and #88
   deliberately doesn't probe or store the root. The three stores also hit the
   same slot (always-replace), so only the depth-3 entry survives anyway.
   The test passes whatever the equal-depth rule does. To exercise the rule,
   preload **interior** positions: for each root child (and optionally
   grandchild), store shallow entries at the depths a depth-4 search would
   *not* use there, with **garbage values** (for example `Exact ±6400`), then
   assert the score is unchanged. A value of 0 can coincide with real scores,
   so use values that can't.

2. **The "midgame" positions are the opening of one game.** Lines 1–12 are
   consecutive plies of a single playout starting from 4 discs: the first
   line is a 2–2 position. The 8 endgame lines are consecutive plies of
   another single game. The scope asks for "≥ 20 representative
   midgame/endgame positions including pass positions and difficult
   endgames". Draw positions from several games, sampled sparsely: midgame
   at about 20–44 discs, endgames at ≤ 12 empties. Tighten `corpus_frozen`'s
   classifier so a 4-disc position doesn't count as midgame, for example
   `mid` requires at least 20 discs. #92's endgame benchmark will reuse
   these lines, so they need real variety.

3. **The TT node gate and the incomplete-store rule are missing.** Both are
   in #89's scope:
   - "TT cuts nodes ≥ 20% on the corpus without time-to-depth regression".
     There is no TT on/off node comparison. Add the corpus-wide node ratio
     for `search_tt` vs `search_limited`, with the threshold as an initial
     target the scope lets you adjust, and record time-to-depth in the
     GREEN notes.
   - "No incomplete result stored for interrupted node/ancestors, completed
     siblings may remain". Run `search_tt` with a small node limit (aborting
     mid-iteration), then a full depth-4 `search_tt` on **the same table**,
     and assert it equals the cold score, over the corpus.

## Minor

4. **The `ordering` switch must be usable outside tests.** Adding
   `ordering: bool` to `SearchConfig` is fine as a real configuration
   option, for ablations. As a switch that only tests flip, it is a
   test-only hook in `src`, which #88's acceptance ruled out. Expose it in at
   least one real caller (`bench --no-ordering`, or a tools agent suffix), or
   argue why the config field alone counts. Also expect breakage: every
   `SearchConfig { eval, endgame_threshold }` literal, including this file's
   `config()` helper, needs the new field.

5. **Say that the expected values are snapshots.** They are the engine's own
   depth-4 scores, which makes them a regression snapshot, not an
   independent oracle. That is fine for equivalence, but say so in the
   header. For the endgame lines, Phase 6 will want exact game-theoretic
   values from a test-side exhaustive minimax. Note that the expected column
   for those lines will change meaning then.

## Nit (non-blocking)

- In `corpus_preload`, the `+6400` and `-6400` stores, and the depth 1 and
  depth 2 stores, all hit the **same slot** for a given child (same key,
  always-replace). Only the last one survives: `Exact −6400` at depth 2. The

  garbage entry per child and say why, or preload grandchildren too if you
  want more than one depth exercised.

# Re-review (round 4, GREEN)

Verdict: **request changes**. The TT gate was lowered on too shallow a
measurement.

## Verified

- I re-ran `./scripts/check.sh` and it exits 0. The full release engine and
  tools suites pass. `ordering: bool` is wired through `negamax` and the
  root, and exposed as `tools match --no-ordering`, so it is not a test-only
  hook. The ordering ablation at depth 5 is a 50% cut, which meets the ≥ 40%
  target.
- The `corpus_preload` nit is taken: one garbage `Exact −6400` at depth 2 per
  child.
- Counts: `search.rs` 279, engine 794, tools 632.

## Required

1. **The TT cut reaches the 20% target at realistic depth.** The notes
   lowered `corpus_tt_nodes` to a 5% bound, based on a 6.4% cut at
   depth 5. TT benefit grows with depth, because transpositions need enough
   plies to occur. I measured the same corpus in release, with a fresh table
   per position:

   | depth | cold nodes | TT nodes | TT / cold | time (both) |
   | ---: | ---: | ---: | ---: | ---: |
   | 5 | 87,508 | 81,852 | 0.935 | 0.04 s |
   | 6 | 341,600 | 303,149 | 0.887 | 0.16 s |
   | 7 | 1,539,423 | 1,266,412 | 0.823 | 0.88 s |
   | 8 | 6,044,483 | 4,807,523 | **0.795** | 3.4 s |

   So the issue's 20% target **is met at depth 8** (and nearly at 7). The
   corpus doesn't show a different scale; the measurement was just too
   shallow. Keep the depth-5 debug test as a regression smoke if you like,
   and add a **release-only** `corpus_tt_nodes_deep` at depth 8 asserting
   TT ≤ 80% of cold. Record this table, or your own run of it, as the
   baseline instead of the 5% concession.

2. **Time-to-depth isn't recorded.** The acceptance asks for "node/time
   numbers … recorded with hardware/build context", and the scope says
   "without time-to-depth regression". The notes give nodes only. Add
   release wall times for TT on and off, and ordering on and off, at the
   gate depth, with the hardware (Apple M2 Pro) and build profile.
