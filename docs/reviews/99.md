# Review: Issue 99 — Incremental tuning against the preceding accepted config

Verdict: **request changes**

## Verified

- #98 was merged, and #97's cut is now recorded. This branch is based on the
  current `main`.
- A protocol section was written before the 200-pair runs, the 10-pair pilot
  is excluded, and five candidates are declared. The runs are equal-node
  (2000 nodes per move, depth lifted to 64 for both sides per #84's rule),
  seeded, on `openings_tune.txt`, with set hashes and hardware recorded.
  The committed base logs carry the run/pair/game IDs, seeds, and
  configuration lines.
- The validation set was used once, to confirm the final choice, not to
  change the engine.

## Required

1. **The decision breaks the predeclared ablation rule.** The protocol says:
   *"An ablation is evidence against a feature if the ablated variant has a
   higher mean than base; otherwise the feature remains."* The results give
   no-frontier 0.8237 and no-disc 0.8337, both **higher** than base 0.8125.
   By the rule declared before looking, that is evidence against frontier and
   against the disc term. The decision then retains both by invoking the
   *retention* threshold ("intervals overlap … the predeclared interval
   threshold is not met"). That threshold was declared for accepting a
   candidate against phase2, not for ablations. Switching rules after seeing
   the numbers is exactly what "predeclare the selection protocol" exists to
   prevent. Either apply the rule as written (remove frontier and disc, and
   re-validate), or record that the ablation rule was badly specified, then
   run a properly predeclared head-to-head test of those two features
   (item 2) before deciding.

2. **The ablations compare against phase2, not against base.** Each variant
   was matched against phase2 separately, and the note compares intervals
   from different runs. Overlapping intervals from two independent matches
   against a third player is not a test of whether variant and base differ;
   it is low-powered and indirect. To attribute gain to a feature (scope:
   "use an ablation to attribute gain to a feature"), play **variant vs base
   directly**, at the same equal-node setup and the same openings, paired.
   Use about 400 pairs per the scope's note (200 is a broad scan, and a
   smaller miss is inconclusive), and a predeclared threshold such as "drop
   the feature if the variant's lower bound is above 0.50, keep it if the
   upper bound is below 0.50, otherwise inconclusive, and default to the
   smaller evaluator". The no-disc result (+2.1 points against phase2) is
   plausible, since raw disc count is often a liability in the midgame,
   so this is worth settling properly.

3. **The ablation runs can't be reproduced or audited.** The variants were
   made by "temporarily zeroing one weight vector … and rebuilding tools",
   with no source variant committed and logs committed **only for the two
   base runs**. The scope asks to record run IDs, configuration, seeds, and
   so on for each candidate. Commit the ablation logs, and make the variants
   reproducible without editing source. For example, add tools agent names
   for the ablations (`ab:4:-mobility`, or a `--ablate frontier` flag) that
   build a `SearchConfig` with a variant `eval` function, all in the tools
   crate, where there are 18 lines of budget headroom, not in the engine.
