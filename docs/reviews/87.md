# Review: Issue 87 — Zobrist hashing and TT depth/domain contract (RED)

Verdict: **request changes** (small)

## Verified

- #86 was merged and closed. This branch is based on the current `main`.
  `cargo fmt --check` passes, and `tests/tt.rs` fails only with E0432 for
  `othello::tt`.
- The three bound cases match PLAN.md, including the edges: `Exact` cuts.
  `Lower` cuts at `value >= beta` (10 vs β = 10 cuts, 9 doesn't). `Upper`
  cuts at `value <= alpha` (0 vs α = 0 cuts, 1 doesn't). The returned values
  are fail-soft.
- The strict equal-depth rule (a depth-4 entry gives no cutoff at depth 3),
  deeper-entry move hints only, no hints from endgame entries, the zero-key
  sentinel, and `clear` are all pinned.

## Required

1. **`index_collision` assumes an index function nobody has specified.**
   Keys 5 and 13 collide only under `key % 8`. PLAN.md allows "`key % len` or
   a multiply mix". Under a multiply mix those keys probably don't collide,
   so the test fails, or, worse, passes for the wrong reason if the second
   store just lands elsewhere and the first is still present. Either fix the
   contract (`index = key % len`, stated in the notes) or expose
   `Table::index(key)` and have the test search for two keys with equal
   indices. The acceptance asks for a *forced* collision, so the test must
   guarantee one.

2. **The endgame bound rules aren't tested.** PLAN.md: "Endgame
   `Lower`/`Upper` bounds may be reused in compatible endgame windows", and
   "the solver never consumes heuristic entries". Only an endgame `Exact` is
   tested. Add:
   - endgame `Lower` cuts at `value >= beta` and not below it, and endgame
     `Upper` likewise;
   - `endgame_cutoff` on a **heuristic** entry returns `None`. This is the
     second half of the domain wall; the first half is already tested.

## Minor

3. **Move the "deep-then-shallow" acceptance item.** #87's acceptance lists
   "deep-then-shallow and forced Zobrist index collision tests", but
   deep-then-shallow is a search-integration property. The notes defer
   integration to #88/#89. Move that clause in skis so #87's acceptance
   matches what it delivers.

4. **Pin the memory and hash constants.**
   `assert_eq!(size_of::<Entry>(), 16)` backs the 64 MB ⇒ about 4 M entries
   arithmetic in `megabytes`. Also pin `zobrist(Board::START)` to its value
   once implemented. The tables are const and frozen, and logs and corpus
   results will rely on stable keys.

# Re-review (round 3, GREEN)

Verdict: **approve**

## Verified

- The tests are unchanged since the RED approval. I re-ran
  `./scripts/check.sh` and it exits 0. Release `tt` is 7/7. The engine is
  733 and `tt.rs` is 107 of 110, with the reallocation approved by you
  (PLAN.md total 915, 84 headroom).
- `zobrist` uses const splitmix64 tables built in a `const fn`, which matches
  the pinned key. `Entry::window` puts the domain check first, then the bound
  rules. `cutoff` adds the strict equal-depth rule, and `move_hint` is
  heuristic-only for deeper-or-equal entries with a real move. `Table` uses
  `key % len`, always replaces, compares full keys, and skips key 0 on both
  store and probe. `size_of::<Entry>() == 16` holds.

## Nits (non-blocking)

- **`megabytes` was promised but isn't delivered.** The RED notes listed
  "`megabytes(mb)` sizing at 16 bytes per entry", and the scope says "Vec
  sized to 64MB memory cap". `tt.rs` has only `Table::new(entries)`. That is
  fine if #88 sizes the table at the call site
  (`Table::new((64 << 20) / size_of::<Entry>())`), but say so in the notes or
  in #88's scope, so the 64 MB cap isn't lost.
- **`tt.rs` is 3 lines from its new limit.** Deriving `Default` (with
  `#[default]` on `Exact` and `Heuristic`) and using
  `vec![Entry::default(); n]` drops the 8-line `EMPTY` constant. `mv`
  defaulting to 0 instead of `NO_MOVE` is harmless, because key 0 never
  matches a probe. That gives #88 some room if it needs a `tt.rs` helper.

Clear to merge.
