# Review: Issue 93 — Benchmark and integrate endgame timing (RED)

Verdict: **request changes** (small)

## Verified

- #92 was merged and closed. This branch is based on the current `main`.
  fmt is clean. `bench_board_position` and `bench_board_timeout` fail as
  intended, because `bench` rejects `--board`.
- `bench --board <me>:<opp>` with an explicit threshold on the corpus
  12-empty position (−2200, verified against the test minimax in #92) must
  report `solved 1` and `Complete`. `--time-ms 0` must report `solved 0` and
  `Fallback`/`Partial`. That is the solver-timeout integration moved from
  Phase 4.
- `endgame_bench` covers 12 empties (seeded plus the corpus line) and
  14 empties with a 1 s root limit, recording completion, median, p90, p99,
  and nodes/s, and asserting the 12-empty median is under 1 s.

## Required

1. **"Fallback strength after an interrupted root solve" isn't measured.**
   It is in #93's scope (and PLAN.md Phase 6's benchmark list). When the root
   solve times out, how good is the move it returns? Measure it: on the
   seeded 14-empty positions, run with a short limit that interrupts the
   solve, then score the returned move with an exact solve
   (`-solve(play(board, best))`), and record how often it keeps the exact
   WDL result and the average centidisc loss against the best move. Record
   it, with no threshold needed. Report `Partial` and `Fallback` separately,
   since `Partial` should never lose the WDL result after #91.

2. **The full-game test doesn't use the solver and allows 5× overrun.**
   `solver_full_game` uses a 50 ms limit and allows `slowest < 250 ms`.
   - The contract's tolerance is `max(50 ms, 10%)`, so for 50 ms the ceiling
     is 100 ms, not 250 ms.
   - At 50 ms the root solve at 12 empties will likely time out every time,
     so the test never shows a *solved* endgame inside a real game, which is
     the point of "full game with solver finishes under the time limit".

   Use a limit where solving is realistic (for example 200 ms, ceiling
   `200 + max(50, 20) = 250 ms`), and assert that **at least one move
   returned `solved == true`**, so the solver is shown to engage in play.
   Record the per-move limit, total time, and slowest move.

## Minor

3. **`bench_board_invalid` passes today for the wrong reason.** It is green at
   RED, because `bench` rejects `--board` as an unknown option, not because
   the board is malformed. Assert the error text (for example stderr contains
   `board`, or `threshold`), and add a **pass root** (a board with no legal
   move for the mover, such as the b2 / a1|c1 fixture). The notes promise
   that `--board` validates "a legal root move".

4. **Record the environment.** The scope asks for hardware, OS, Rust version,
   and build settings with the numbers. Include `rustc -V` and the release
   profile (LTO, codegen units) in the GREEN notes next to the bench output.
