# Review: issue 122, engine pattern definitions, features and stage

## RED round 1 (commit 4c1de31)

Verdict: **request changes**.

I checked the three hand-computed indexes digit by digit against the
board (`me` a1, d1, b2; `opp` c1, f1, d2, g2, d4, h8). All three are
right: 46,459, 13,897 and 4,432.

Required:

1. **`index_convention` will fail in GREEN for two of its three cases.**
   Your notes define `features` as the family offset plus the base-3
   index, and the `feature` helper returns that value unchanged. Corner
   2x5 has offset 78,732 and diagonal 8 has offset 157,464, so the helper
   returns 92,629 and 161,896, not 13,897 and 4,432. Subtract the
   instance's offset in the helper, and keep the table in the notes as
   local indexes.
2. **`canonical` does not belong in the engine.** It exists for weight
   sharing, which only the trainer does. The engine is the part a reader
   studies to see how the program plays, and its evaluator has 230 lines
   to spend. This reverses a sentence in the issue, which invited a shared
   home for the permutations; that sentence was mine and it was wrong.
   - Remove `canonical` from the intended engine API and
     `canonical_symmetry` from `tests/pattern.rs`.
   - The permutations and their tests move to the trainer in issue 124,
     where the trainer can use `othello_tools::sym` for the transforms.
3. **Replace it with the engine's own symmetry property.** Add
   `instances_closed`: for every instance and every one of the eight
   symmetries, the transformed set of squares is the square set of some
   instance of the same family. That is what makes the pattern set
   symmetric, and it needs nothing from the trainer.
4. **`features` is only checked on three identity instances.** Add
   `features_reference`: for every one of the 46 instances, compute
   offset plus the sum of digit × 3^position directly from
   `instance.squares` in the test, and compare with `features`. Use at
   least three dense positions (the bench corpus has them) as well as the
   start position. This pins the digit order for the transformed
   instances, which nothing else does.
5. **`index_ranges` uses two nearly empty boards.** Run it over the same
   dense positions as item 4.
6. **`stage_boundaries` tests one side of each boundary.** Add the other
   side: 59 and 56 are stage 0, 51 is stage 1, 6 is stage 10, 4 and 1 are
   stage 11.

Note, no action: `instances_match_symmetries` pins the order of instances
to `Sym::ALL`. Nothing depends on that order except the layout fingerprint
in issue 124, so it is a harmless pin. Keep it.
