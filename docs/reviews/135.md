### Major: Add the promised corpus score and optimal-move checks at depths 1–8

Location: `tests/search.rs:151–209`, `tools/tests/golden.rs:379–414`;
SKIS #135, first RED test requirement.

The issue calls for the corpus to retain its scores at every depth from
1 through 8, with changed best moves accepted only when their child value
proves them equally good. That test is absent. `window_equivalence` uses
the synthetic `noise` evaluator, one selected depth per position, and
checks only the TT result's chosen move. The existing standard-evaluator
golden remains a depth-8 snapshot; `fewer_nodes` checks only node totals.
Existing depth-4 corpus tests do not fill the missing depths either.

Before changing the search, record the original engine's corpus scores
for all eight depths and add executable comparisons against that fixed
reference. Cover the search entry points being changed and validate the
chosen move's value, so legitimate ties can pass without blindly
re-recording a changed best move. Preserve the pass-root and terminal
conventions and the exact-solve cases. When checking a chosen child,
preserve the original root's heuristic/exact domain: calling a top-level
search on that child can otherwise activate the endgame threshold one
move earlier than the original search.

The reference scores must remain fixed when the node columns are updated
in GREEN. A release-only placement for the expensive coverage is fine;
this does not need to make every debug test run slow.

### Major: Preserve the frozen v1.0.0 fingerprint's meaning

Location: `docs/prs/135.md`, "Expected in GREEN";
`tools/tests/golden.rs::GOLDEN_V1`; `docs/PLAN.md`'s frozen v1.0.0
fingerprint and versioned-baseline requirements.

The notes propose re-recording the node columns of both `golden_v1` and
`golden_v2`. The issue explicitly authorizes re-recording `golden_v2`.
Replacing v1.0.0's historical node counts with those from a new PVS search
would turn the purported frozen reference into a moving one.

Keep the original v1.0.0 fingerprint intact. If the current shared search
also changes the `classic` comparator, give that current-search snapshot
its own explicit identity and document the distinction. Adjust how the
tests exercise those references as necessary; this request does not
require duplicating the legacy engine in production code. Continue to
use an actual versioned engine artifact for comparisons described as
being against frozen v1.0.0. Resolve this before re-baselining the GREEN
results, so the review can distinguish intentional work reduction from
an overwritten reference.

### Notes and non-blocking suggestions

- The 1,000 heuristic samples plus 200 exhaustive endgames are a useful
  independent oracle across direct, iterative and TT entry points. The
  issue does not explicitly require an even depth distribution; retaining
  twenty depth-5 cases to keep debug runtime reasonable is acceptable
  alongside the requested corpus coverage. No even-spread rerun is
  requested.
- A few explicit fail-low/fail-high and alpha/beta-boundary cases against
  known minimax values would strengthen the null-window contract,
  particularly when a bounded search seeds a table reused by a wider
  search. Existing full-root comparisons should remain as well.
- `FULL_WINDOW_NODES` equals the original `GOLDEN_V2` sum, 3,791,452.
  Keep this baseline fixed when current node expectations are updated.
  The deterministic node guard complements the registered wall-time gate;
  it does not replace that measurement.
- The proposed first/full, later/scout, strictly-interior/full-research
  scheme is appropriate. The planned missing-research mutation check in
  GREEN will provide useful evidence that the oracle detects that bug.
