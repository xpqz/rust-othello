## Summary

## Findings

### Major: The 5% acceptance gate does not measure completed search work consistently

Location: `tools/examples/search_rate.rs:34–38,53–58`;
`src/search.rs:368–385`; `docs/prs/133.md:35–40,57–60`; SKIS #133,
measurement and revert criteria.

The driver divides `SearchResult.nodes` by the entire three-second call.
On an interrupted iteration, `search_inner` exits before copying that
iteration's `ctx.nodes` into the returned result. The numerator therefore
counts all completed iterations, while the denominator also includes work
in the aborted next iteration. A faster engine can spend more of its
budget in that omitted iteration without completing it, and show little
gain; crossing an iteration boundary can produce a large apparent gain
unrelated to the true throughput change. The #131 notes already identify
this reason for removing timed-search NPS from that experiment.

The aggregate adds a second problem: it mixes twelve timed midgames with
eight exact solves, some lasting only tens of microseconds. Pattern-index
work does not speed up those exact searches, and their rates affect the
single reported median. This is a poor gate for the targeted midgame
optimization and is sensitive to short-call timing noise.

Keep the three-second searches as a separate depth/playing-strength
observation. Gate speed on elapsed time for a fixed, fully completed
search workload with pinned results and node counts, using cold tables
consistently before and after. Repeat or batch short searches so timer and
startup costs cannot decide a 5% result; report midgame and exact-solve
results separately. Fix the aggregation/acceptance rule in the issue and
notes before the comparison, with an explicit repetition and noise rule.
Append a replacement baseline and mark the existing 2,709,457 figure as
the old completed-iteration-count statistic, unsuitable as the speed
baseline. Preserve the original log. This needs only short benchmark runs,
not a repeat of #131's matches.

### Minor: Remove the issue number from the source comment

Location: `tools/tests/golden.rs:213–214`.

The `GOLDEN_V2` comment says "as of issue 133". Keep that provenance in
the PR notes and describe the invariant in the source comment, as required

### Note: Step 1 equivalence tests are appropriate

`features_wide` checks all 46 indices on the 23 corpus boards, empty and
both full one-colour boards, and 100,000 reproducible disjoint random
boards. Its square-by-square reference is independent of the proposed row
lookup algorithm. Existing symmetry/index-convention tests additionally
check the instance definitions shared by the reference.

`golden_v2` pins move, score and nodes for the standard evaluator at depth
8, retaining the established pass-root and terminal conventions. Production
source and assets are unchanged from `d173987`, so passing these tests now
is expected and appropriate for a pure optimization. Do not manufacture a
failing behavioural test merely to label this RED. Move-generation tests
remain a separate step 2 gate, as specified in the issue.

The row-table design is plausible within the budget: local ternary indices
fit in `u16`, and offsets must be added after widening. The 188,416-byte
table and its one-time construction should be included when describing
the eventual memory/startup cost. No implementation is approved by this
tests-only review.
