## Required

1. **Reusing openings produces a false strength claim.** Each split has
   **four** openings, and `match` cycles them with `pair % openings.len()`.
   The Phase 3 gate command shows the effect:

   ```
   match --a phase2 --b greedy --pairs 200 --seed 1
   pairs 200 … mean 0.8125 interval [0.7837, 0.8413] bootstrap elo [223.69, 289.68]
   match --a phase2 --b greedy --pairs 4 --seed 1
   pairs 4 …   mean 0.8125 interval [0.1334, 1.0000] uninformative elo none
   ```

   Both agents are deterministic, so the 200 "pairs" are the same 4 pairs
   copied 50 times. The bootstrap treats them as 200 independent samples and
   reports a tight interval and an Elo range. That is exactly the
   overconfident claim the statistics policy exists to prevent. Two changes
   are needed:
   - `match` must not reuse an opening within a run. Reject
     `--pairs > openings.len()`, or default `--pairs` to the set size.
   - The frozen sets must be big enough for the gate (`--pairs 200` from
     `validation`) and for the plan's 55% claim (about 400 pairs). That means
     hundreds of openings per split. Hand-written lines won't scale. Generate
     them once, deterministically, for example by enumerating legal 4–8-ply
     lines, grouping by canonical key, and assigning groups to splits by key
     order. Commit the files with the generator's description in a `#`
     header. Generating them doesn't violate "no seeded opening generation":
     that rule is about generating openings during matches.

2. **The game-0 log records game 1's seeds.** In `match_command`, `a_seed`
   and `b_seed` are reassigned for game 1 *before* both log lines are pushed.
   So the game-0 `GameLog` gets
   `agent_seeds: (stream(pair,1,1), stream(pair,1,0))`, which is wrong, and a
   reader can't reproduce game 0 from its log. Bind the game-0 seeds to their
   own names, or push each log line straight after its game. Add a test that
   game 0's logged seeds equal `stream(seed, pair, 0, 0/1)`, or that two log
   lines in one pair carry different seeds.

3. **The tools crate is at 600/600 with Phase 3 unfinished.** The
   `tune` and `positions` commands are deferred, and #81 (harness tests,
   baseline ladder) is still to come. Item 1 needs either a generator command
   or a committed one-off script. There is no room for any of this. AGENTS.md
   says to stop and discuss before contorting code or exceeding the budget.
   `main.rs` is 171 lines and has the obvious slack:
   - the two near-identical `GameLog { … }` literals and the paired
     `make_agent` / `play_game` blocks become one loop over
     `[(a, b), (b, a)]`;
   - `GameLog::line` could be a `Display` impl with a shorter format;
   - the `depth` closure duplicates `make_agent`'s `ab:` parsing.

   Cut, then report what's left. If Phase 3 still doesn't fit, bring a
   reallocation or scope proposal to the user, not to the review.

## Minor

4. **Hard-coded log fields.** `run: 1` is constant. Use the `--seed`, or a
   run id derived from it, so logs from different runs can't be confused.
   `depth` logs `max(depth(a), depth(b))`, which is wrong for an asymmetric
   match such as `ab:2` vs `phase2`. Log each side's depth, or drop the field,
   since `describe` already records it.

5. **The default `--openings` path is compiled in.** It uses
   `concat!(env!("CARGO_MANIFEST_DIR"), …)`, which is an absolute path on the
   build machine. That is fine for a dev tool, but say so, or resolve
   `bench/` relative to the working directory.

6. **The PR notes have no RED section.** Following on from the process note,
   the notes merge RED and GREEN. Future PRs should keep them separate, as
   AGENTS.md expects.
