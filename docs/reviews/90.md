# Review: Issue 90 — Exact endgame solver with domain and solved semantics (RED)

Verdict: **request changes**

## Verified

- #89 was merged and closed. This branch is based on the current `main`.
  fmt is clean, and the target fails only with E0432 for `othello::solver`.
- `src/solver.rs` is sanctioned by #90's scope ("Budget: add
  src/solver.rs"), even though PLAN.md's Phase 6 text says `src/search.rs`.
- The test-side `exact` is independent of production ordering and the TT.
  Alpha-beta from `(-INF, INF)` returns the exact value, and it handles
  terminal and pass the same way as the contract.

## Required

1. **The reference sample is one position.** `solve_matches_reference` and
   the trigger and domain tests all use `endgame_board(6)`, the **first**
   corpus line with ≤ 6 empties. The acceptance says "solver matches
   reference on the documented sample", and PLAN.md's test strategy
   specifies "a documented seeded sample of 1,000 positions with 6–10
   empties compared against a slow reference … (release-only `#[ignore]`)".
   Add the seeded sample: playouts stopped at 6–10 empties, with the seed and
   count documented. Run a small slice (for example 20 positions at 6–8
   empties) in debug, and the full 1,000 at 6–10 release-only.

2. **"Interior nodes remain heuristic" isn't tested.** It is an acceptance
   item ("no interior solver calls"). Use a root **above** the threshold
   whose subtree crosses it. For example, set `endgame_threshold` to the root
   empties − 1, search at a depth that reaches below the threshold, and
   assert `solved == false` and that the score equals the heuristic
   `negamax`/`search_limited` result with the solver disabled (threshold 0),
   not the exact value. Choose the fixture so heuristic and exact differ, and
   assert that difference too, or the test is vacuous.

3. **The domain wall isn't tested from the solver side.** The scope says
   "Solver never consumes heuristic entries", and PLAN.md lists "TT preloaded
   with shallow heuristic entries" for the solver. Preload garbage heuristic
   entries (`Exact ±6400` at assorted depths) for the root's children, run
   the solver through `search_tt`, and assert it still matches `exact`. The
   reverse direction (heuristic search ignores endgame entries) is unit-tested
   in #87, but one integration check here, preloading endgame garbage before
   a heuristic search above the threshold, would close the loop.

## Minor

4. **Known positions.** The acceptance says "known positions match". If
   "known 12-empty positions" belong to #93's benchmark issue, say so in the
   notes or in skis. Otherwise add one or two hand-verified (or
   reference-verified, release-only) 12-empty positions here.

5. **What `depth` means on a solved result.** `solver_root_trigger` pins
   `depth == 0` for a solved root. State that convention on `SearchResult`
   (0 = exact solve, not a heuristic depth), because tools and logs read
   `depth`.

# Re-review (round 2)

Verdict: **request changes** (one test can't work as written)

- Items 1, 3, 4, and 5 are addressed. There is a seeded sample
  (`0x5A3A11`, 20 positions at 6–8 empties in debug, 1,000 at 6–10
  `#[ignore]`), both domain-wall integrations, known 12-empty positions in
  #93's scope (checked in skis), and the `depth = 0` convention for GREEN.
  I grepped the committed tree and every test the notes name is present.
- **Item 2: `solver_interior_is_heuristic` will panic in GREEN.** It looks for
  an 8-empty position where `search_limited(.., depth 10, threshold 0)`
  differs from the exact solve. But at depth 10 from 8 empties, heuristic
  search reaches every terminal: there are at most 8 placements, passes cost
  no depth, and terminal positions are resolved before the cutoff. So the
  "heuristic" result is the exact value for every position, `find` never
  matches, and `.expect("fixture where exact and heuristic differ")` panics.
  Use a depth **below** the empties, for example depth 2 or 3 at 8 empties
  with `endgame_threshold = 7`. Children sit at 7 empties (≤ threshold, so a
  wrongly-placed interior solver call would fire), and leaves are heuristic,
  so heuristic and exact genuinely differ.
- `heuristic_ignores_endgame_entries` has the same depth-10-at-8-empties
  setup. It still passes as a domain check, but it becomes much sharper
  at a non-terminal-reaching depth: the garbage endgame entries would then be
  the only possible source of a difference. Use the same smaller depth there.
- fmt is clean, and the target fails only with E0432.

## Nit (non-blocking)

- `solve_sample_deep` uses a bare `#[ignore]`. Use
  `cfg_attr(debug_assertions, ignore = "release-only")`, matching the other
  heavy tests, so `cargo test --release` runs it.

# Re-review (round 3)

Verdict: **request changes**. The fix is only half applied.

- `heuristic_ignores_endgame_entries` now uses depth 3 for both searches, and
  `solve_sample_deep` uses the release-only `cfg_attr`.
- **`solver_interior_is_heuristic` still fails.** Only the fixture-selection
  `find` moved to depth 3. The two searches the test actually asserts on are
  still **depth 10** (lines 23 and 28 of the function):

  ```rust
  let result = search_limited(board, SearchLimits::depth(10), &config);
  …
  search_limited(board, SearchLimits::depth(10), &probe).score
  ```

  At depth 10 from 8 empties, both reach every terminal and return the exact
  value. So `assert_ne!(result.score, exact_score)` fails for the very
  fixture the `find` chose because it differs at depth 3. Change both to
  depth 3, to match the selection. A single `let limits = SearchLimits::depth(3);`
  used in all three places prevents this drift.
- fmt is clean, and the target fails only with E0432.
