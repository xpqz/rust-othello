# Review: issue 124, fit, restart, learning report, inspect, asset, evaluate

## RED round 1, checkpoint 1 (commit 2c3cdb3)

Verdict: **request changes**. The API is sensible. Several tests would
pass on a fit that does not work, and one cannot pass at all.

On your budget note: the user's ruling stands. The trainer guard is 650
and the 450 in the issue text is superseded. No further ruling is needed.

I checked `reference` by hand: the least-squares answers are 1.8 and 2.8,
the count-once answers are 2.5 and 4.0, and the design's update has its
fixed point at the right place. That test is good.

Required:

1. **`tied_asset` cannot pass.** Stage values run up to 1,672 discs, which
   is 167,264 centidiscs and far outside `i16`. By the quantisation rule
   `asset` must return an error, so `unwrap` panics. Use small values.
   Then make the test bite:
   - it currently passes if `asset` writes all zeros. Assert that every
     written value equals the quantised input at its canonical index;
   - give each stage different values and assert that stage `s` of the
     file holds stage `s` of the input.
2. **`canonical` has no tests of its own.** The trainer learns one value
   per tied pair, so a wrong permutation silently teaches wrong weights.
   Issue 122 moved these tests here. Add:
   - hand-computed pairs, with the digits in the notes. One is already
     worked: the edge index 46,459 from issue 122 mirrors to 35,577, so
     both map to 35,577. Add one each for corner 3x3 (transpose), a row
     and a diagonal (both reversed);
   - corner 2x5: `canonical(i) == i` for every index in its range;
   - for every index: the result is in the same family's range, is not
     larger than the input, and `canonical(canonical(i)) == canonical(i)`;
   - on the start position and three dense positions, a board and its
     seven transforms (from `othello_tools::sym`) give the same sorted
     multiset of `canonical(features)`. And a control: without `canonical`
     the multisets differ for at least one transform.
3. **`damping` does not test damping.** Labels 1, −1, 1 have a
   least-squares answer of 0.33, so a fit with no damping at all passes
   `< 0.5`. Use one rare entry seen three times with label +10 and one
   common entry seen several hundred times with label +10, held-out equal
   to training so early stopping does not interfere. Assert that the
   common entry ends near 10 and the rare one stays below a stated
   fraction of 10. State the bound in the notes with the arithmetic from
   the constants: after `max_passes` the rare value is at most
   `10 × (1 − (1 − 3 × step / floor)^max_passes)`. The production
   constants must then satisfy this test.
4. **`planted` cannot tell learning from barely learning.** Each example
   carries all 46 features, and the 38 that are not planted are mostly
   one-off configurations that soak up the residual. The 1.0 threshold
   sits just under the error of always guessing zero (about 1.4), so it
   proves little. Build the examples from the instances of the two
   planted families only, so nothing else can absorb the signal, and
   require a held-out mean absolute error below 0.05 discs and below 5%
   of the error of guessing zero.
5. **`reference` has no shared credit.** No example contains both
   entries. Add a case where they occur together, with multiplicity:
   features `[0, 0, 1]` label 5, `[1]` label 1, `[0]` label 2 has the
   exact answer (2, 1).
6. **Early stopping is untested.** Add `early_stop`: a held-out set that
   disagrees with the training set, so held-out error falls and then
   rises. Assert that the returned values are those of the best pass, not
   the last, and that the curve stops `patience` passes after the best,
   well short of `max_passes`.
7. **`inspect_output` asserts almost nothing.** The string "10" appears in
   nearly any output. With the values in the test the occurrence-weighted
   mean is 15/35 = 0.43, so the relative values are −2.43, +2.57 and
   +0.57. Assert those numbers, highest first, and that entries with no
   occurrences are not listed.
8. **Process-level restart and repeatability belong to this checkpoint.**
   The point of checkpoint 1 is to prove the pipeline before the long
   run. Add, on a small synthetic archive as in the label tests:
   - a `fit` run killed after its first stage file appears, then resumed,
     gives the same asset bytes and the same report as an uninterrupted
     run;
   - two label journals with the same lines in a different order give the
     same asset bytes.
9. **The split.** Test that the held-out choice depends only on a game's
   move bytes: the same game is held out or not wherever it sits, and
   over a few hundred distinct games roughly one in twenty is held out.

Smaller:

- `quantisation`: add infinity, and the two edges of the range (327.67
  passes, 327.68 fails). Assert that the error names the entry.
- `report_fields`: also require the toolchain line and the per-pass curve
  values, since the design names both.
- `reproducible` on two tiny in-process fits proves little once item 8
  exists. Keep or drop it, your choice.

For GREEN, not tests:

- `Example.features` as a `Vec<u32>` means one allocation per position.
  The full archive is about eight million positions. Build the examples a
  stage at a time and report peak memory and time per stage from the
  pilot fit. The time decides the restart unit, as the design says.
