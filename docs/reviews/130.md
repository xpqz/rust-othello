## Ladder run 1: stopped by a driver defect (12 Nov, 09:03–09:29)

Verdict: request changes. No calibration result yet.

The run from `cb1f5ce` played level 1 and then exited with status 2:

```
level 1 pairs 38 games 76 W 75 D 0 L 1 mean 0.9868 [0.9605, 1.0000] disc_diff 45.72 edax_ms_per_move 0.00 seed 1 resamples 10000
replaying 12 pairs
journal header mismatch:
 expected header v1 level 1 … date 2026-11-12T08:29:01Z …
 found    header v1 level 1 … date 2026-11-12T08:03:47Z …
```

The first 12 pairs were voided because another session was compiling
(load up to 22). That exposed two defects; both should have been caught
in my review of `cb1f5ce`, which accepted the resume claim unverified.

1. **Resume never works.** `header()` puts `utc_date()` in the journal
   header, and the journal refuses to open when the header differs. Any
   second open of a journal fails: the in-run replay of voided pairs and
   a re-run after an interrupt alike. The notes' claim "Re-running the
   same command resumes from the journal" is false for the committed
   tree. Fix: the header holds only what must be identical for results
   to be comparable (level, engine, time, Edax path and hashes, commit,
   openings and hash, jobs, max load). Record the date elsewhere, for
   example a line in the log.
2. **No interrupt-and-resume test.** The definition of done requires it
   for jobs over ten minutes. RED first: a test that runs a short level,
   kills it part-way (or runs it twice), re-runs the same command and
   gets the same summary line, with no game replayed that was already
   valid. It must fail on `cb1f5ce` with the header mismatch.
3. **Edax time is truncated to zero.** `edax_ms` adds
   `as_millis()` per move, so 1,779 level-1 moves sum to 0 ms. Sum the
   elapsed `Duration` per game and convert once (or record microseconds).
4. **Progress line.** `pair {done} void` prints the completion count,
   not the pair number. Print the pair id.

Also say in the notes what the stop rule does with an incomplete level:
`run_level` returns an error after ten attempts, which is right; state it.

After the fix, the reviewer re-runs the whole ladder from the new commit
with the same command, starting level 1 afresh (the old journal's header
format will not match, and 25 minutes is cheap). The 38 valid pairs
above are not carried forward and are not a result; they are recorded
here only as evidence of the failure. The failed log and journal stay in
the worktree `othello-edax-ladder` until the re-run is complete.

## Kill case, `8d57657` (12 Nov)

Verdict: request changes to the test only. Not run here: the ladder is
using the machine. Do not run it, or anything else heavy, until the
ladder finishes.

`kill_run … &` backgrounds a shell function, so `$!` is the subshell
that runs the function, not the driver. `kill -9` ends the subshell and
the driver keeps playing; the second `kill_run` then shares the journal
with it. I made the same mistake in my first hand check (zsh): the
resumed run reported "replaying" nine times while the first driver was
still writing. The script can pass in that state, so it does not test a
kill.

- Start the driver directly (`"$BIN" … &`) or `exec` it inside the
  function, so `$!` is the driver.
- After the kill, assert that no `edax_ladder` process with this
  journal path is alive before resuming.
- Check for orphaned Edax processes right after the kill as well as at
  the end.

Run it after the ladder completes and record the output in the notes.
