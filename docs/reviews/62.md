# Review: Issue 62 — Implement score contract and tests (RED)

Verdict: **request changes**

## Verified

- The branch is cut from `main` after the #61 merge. #61 is closed and its
  branch is deleted.
- `cargo test --test score` fails with exactly the E0432 recorded in the PR.
- The tests cover the right items: `SCORE_SCALE`, `INF`, `EVAL_BOUND`, pure
  `terminal_score`. No `Board` dependency.

## Required

1. **Two assertions will fail clippy once the tests compile.**
   `assert!(-INF > i32::MIN)` and `assert!(EVAL_BOUND < INF)` compare `const`
   items, so `clippy::assertions_on_constants` fires and
   `cargo clippy --all-targets -- -D warnings` fails. I confirmed this in a
   scratch crate with the same constants. GREEN cannot meet the definition of
   done with these lines as written. Use compile-time checks
   (`const _: () = assert!(EVAL_BOUND < INF);`), or express the property through
   a runtime operation (see 3).

2. **`terminal_score_range` copies the implementation.** It asserts
   `terminal_score(d) == d * SCORE_SCALE`, which is the formula itself, so it
   can only fail if the function is a different function. Together with
   `scale_is_centidiscs` it adds nothing. Replace it with properties of the
   contract, checked for every `d` in `-64..=64`:
   - antisymmetry: `terminal_score(-d) == -terminal_score(d)`;
   - strictly increasing: `terminal_score(d) < terminal_score(d + 1)`;
   - inside the eval range: `terminal_score(d).abs() <= EVAL_BOUND`;
   - strictly inside the search window: `-INF < terminal_score(d) < INF`.
     Search relies on this: any real score must beat the initial `-INF` alpha.

   Keep the spot values in `scale_is_centidiscs` (0, ±1, ±64). They pin the
   scale.

3. **The overflow tests don't test the arithmetic search will do.**
   `window_arithmetic` checks `±INF ∓ EVAL_BOUND`, but nothing in PLAN.md does
   that, and pinning `-993_600` is a magic number. Search negates windows
   (`-beta, -alpha`), opens null windows (`alpha, alpha + 1` and `beta - 1`),
   and may widen aspiration windows. Test those operations on the extremes,
   with checked arithmetic so a regression fails rather than wraps:
   - `INF.checked_neg() == Some(-INF)` and `(-INF).checked_neg() == Some(INF)`;
   - `INF.checked_add(1)` and `(-INF).checked_sub(1)` are `Some`.

   With that, the `-INF > i32::MIN` assertion in item 1 becomes redundant.

## Minor

4. **Pin the types.** PLAN.md says every value is an `i32`. One line keeps a
   later edit from widening or narrowing them unnoticed:
   `let _: (i32, i32, i32, fn(i32) -> i32) = (SCORE_SCALE, INF, EVAL_BOUND, terminal_score);`

5. **Acceptance items this issue cannot cover.** "No search or eval module
   mixes disc units and centidiscs", "evaluate stays within EVAL_BOUND", and
   "Phase 1 wiring tested on real boards" all need code from later phases. Say
   in `docs/prs/62.md` which later issue covers each one, so #62 can close
   without implying they are done.

6. **Where the documentation goes.** The objective and the "heuristic +6400
   may outrank a small proven win" note belong in `src/score.rs` doc comments
   per the issue. #63 records conventions in `src/lib.rs`. Don't write the
   same text twice: put it in `score.rs` and refer to it from `lib.rs` if
   needed.

7. Fold `eval_bound_fits` into the property test from item 2. The
   `assert_eq!(EVAL_BOUND, 6_400)` pin can stay.
