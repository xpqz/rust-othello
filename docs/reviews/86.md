# Review: Issue 86 — Move ordering with fixed buffers (RED)

Verdict: **request changes** (small)

## Verified

- #85 was merged and closed. This branch is based on the current `main`.
  `cargo fmt --check` passes, and the target fails only with E0432 for
  `ordered_moves`.
- I hand-checked `ordering_priorities`. a1 (east: b1 opp, then c1), b2
  (north: b3 opp, then b4), and g4 (west: f4 opp, then e4) are legal, and
  `len == 3` pins that they are the only moves. The expected order
  `a1, g4, b2` can't come from square order (b2 = 9 < g4 = 30), so it
  genuinely tests corner, normal, X.
- `ordering_start_ties` pins preferred-first and square-index ties: f5, then
  d3 (19), c4 (26), e6 (44).
- Score preservation (the acceptance) is already covered by the existing
  `minimax_equivalence`, which will exercise interior ordering through
  `negamax`.

## Required

1. **The depth ≥ 2 rule isn't tested.** The scope's distinctive rule, "moves
   minimising opponent replies only at depth >= 2", has no test. Both tests
   call `ordered_moves` at depth 1, where it is meant to be off. Add a fixture
   with two normal-category moves where the higher-index one leaves the
   opponent fewer replies:
   - at depth 2 it sorts first;
   - at depth 1 the same pair falls back to square order.

   That pins the rule and its depth gate together.

2. **C-squares aren't tested.** The scope puts "X/C squares last", but the
   fixture has only an X-square (b2). Add a C-square move, such as b1 or a2
   style edge-adjacent-to-corner, in the last bucket. If the categories are
   implemented as one mask, one C case is enough to pin that the mask
   includes the C squares.

## Minor

3. **Budget.** `search.rs` is 180 of 210. Ordering, the #88 TT probe and
   store, and the Phase 6 root solver all land in `search.rs`. In GREEN,
   report the post-ordering count, and if it leaves less than about 15 lines,
   raise the `search.rs` reallocation with the user now, from the 164-line
   engine headroom, rather than mid-#88.

# Re-review (round 5, GREEN)

Verdict: **request changes**: budget workarounds

## Verified

- The tests are unchanged since the RED approval. I re-ran
  `./scripts/check.sh` and it exits 0. The full release suite passes, and
  `minimax_equivalence` still holds, so ordering doesn't change scores.
- `ordered_moves` matches the scope. It uses fixed `[u8; 64]` and
  `[u32; 64]` buffers with an in-place selection sort and no heap. The key is
  `rank << 16 | replies << 8 | square`: preferred, corner, normal, X/C, then
  replies at depth ≥ 2 only, then square index. The `XC` mask is right: b1, g1,
  a2, b2, g2, h2, and the mirrored squares on ranks 7 and 8. The root passes
  the previous best, and interior nodes pass `None`.

## Required

1. **Moving `SearchConfig::standard()` into `eval.rs` is a budget dodge.**
   The notes say it was moved "so the ordering code fits the `search.rs`
   allocation". That puts an `impl` of a search type in the evaluator and
   reverses the dependency: `eval.rs` now imports `crate::search`. Its only
   purpose is to make one file's count look smaller, while the engine total
   is unchanged. AGENTS.md: "Do not use hacks, loopholes … to meet the size
   budget … If the work cannot fit, stop and discuss." Move it back, let
   `search.rs` read about 217, and raise the reallocation, which the notes
   already say #88 and Phase 6 will need.

2. **Single-letter names were bought for budget.**
   `ordered_moves(b: Board, m: u64, d: u32, p: Option<u8>)` breaks the
   naming used everywhere else in `search.rs` (`board`, `moves`, `depth`).
   It looks chosen to keep the signature on one rustfmt line. Use
   `board, moves, depth, preferred`. Readability is part of the definition
   of done, and the cost is a line or two that belongs in the honest count.

## For the user: `search.rs` reallocation

- With item 1 undone, `search.rs` is about 217 of 210. #88 (TT probe and
  store) and the Phase 6 root solver still have to land there. The engine is
  622 of 999, with 164 lines of unallocated headroom. I suggest raising
  `search.rs` to about 260 now, so #88 and #92 have a stated target instead
  of each squeezing past the limit. Your call.
