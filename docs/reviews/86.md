# Review: Issue 86 — Move ordering with fixed buffers (RED)

Verdict: **request changes** (small)

## Verified

- #85 was merged and closed. This branch is based on the current `main`.
  `cargo fmt --check` passes, and the target fails only with E0432 for
  `ordered_moves`.
- I hand-checked `ordering_priorities`. a1 (east: b1 opp, then c1), b2
  (north: b3 opp, then b4), and g4 (west: f4 opp, then e4) are legal, and
  `len == 3` pins that they are the only moves. The expected order
  `a1, g4, b2` can't come from square order (b2 = 9 < g4 = 30), so it
  genuinely tests corner, normal, X.
- `ordering_start_ties` pins preferred-first and square-index ties: f5, then
  d3 (19), c4 (26), e6 (44).
- Score preservation (the acceptance) is already covered by the existing
  `minimax_equivalence`, which will exercise interior ordering through
  `negamax`.

## Required

1. **The depth ≥ 2 rule isn't tested.** The scope's distinctive rule, "moves
   minimising opponent replies only at depth >= 2", has no test. Both tests
   call `ordered_moves` at depth 1, where it is meant to be off. Add a fixture
   with two normal-category moves where the higher-index one leaves the
   opponent fewer replies:
   - at depth 2 it sorts first;
   - at depth 1 the same pair falls back to square order.

   That pins the rule and its depth gate together.

2. **C-squares aren't tested.** The scope puts "X/C squares last", but the
   fixture has only an X-square (b2). Add a C-square move, such as b1 or a2
   style edge-adjacent-to-corner, in the last bucket. If the categories are
   implemented as one mask, one C case is enough to pin that the mask
   includes the C squares.

## Minor

3. **Budget.** `search.rs` is 180 of 210. Ordering, the #88 TT probe and
   store, and the Phase 6 root solver all land in `search.rs`. In GREEN,
   report the post-ordering count, and if it leaves less than about 15 lines,
   raise the `search.rs` reallocation with the user now, from the 164-line
   engine headroom, rather than mid-#88.
