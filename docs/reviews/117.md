## Gate 2 amendment: `--max-load 6` (reviewer error, fixed before any result)

The pre-registered gate 2 command used `--jobs 4 --max-load 4`. That setting
cannot produce valid pairs: the tool records the one-minute load average for
each pair and voids a timed pair whose load exceeds `max-load`, and the
match's own four search threads hold the load at four or more. I approved
that command in round 1, so the error is mine as much as the implementer's.

What happened:

- The first gate 2 run started at 22:33 on 10 November. All 16 game records
  it wrote (8 pairs) had load between 4.0 and 5.5 and were void.
- The run was stopped. Its journal and log were set aside, not committed.
  Only the load values were read; no score from that run was examined.
- With the user's decision, gate 2 was relaunched with `--max-load 6`: four
  match threads plus at most two of ambient load on six performance cores.
  The launcher waits for the load average to fall below 2 before it starts.
- Nothing else changed: `pc:100:500` vs `pc:off:500`, 1,000 pairs, seed 117,
  jobs 4, `bench/openings_probcut2.txt`, worktree pinned at `6f14e1a`,
  lower bound above zero, no extension.

Required in the notes when gate 2 completes:

- State this amendment and the reason in `docs/prs/117.md`.
- Report the number of void pairs. If any remain, re-run the same command
  until all 1,000 pairs are valid, then report.
- Gate 3 uses `--max-load 6` as well, for the same reason.
