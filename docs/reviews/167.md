# Review of #167 — Play with the game clock

## RED review of `f375778`

**Request changes.** Add RED coverage for the clock wiring in the
play paths before proceeding to GREEN.

1. **Major — CLI play can still use flat search and pass the revised
   test.** In `tests/cli.rs::play_opponent_is_search` the 51 s wall-time
   assertion passes with the current 3 s search, and would also pass
   with an instant legal-move selector. `play_agent_policy` covers the
   factory in isolation. It would pass if `src/cli.rs::play_game` never
   called it, never called `clock`, or passed 51,000 again before every
   move. Add a deterministic test of the CLI's actual turn path that
   observes the first clock update and the next update after a scripted
   charge. Cover the forced move and pass behavior there without a
   wall-time bound on the subprocess. The existing subprocess check can
   still serve as a legal-reply smoke test.

2. **Major — The GUI tests cover fresh limits and accounting in
   isolation.** `gui::engine_clock_default` also passes with an allocator
   that always receives 51,000. `gui::engine_clock_undo` calls
   `engine_moved` directly and refunds back to the full clock, so it
   misses a result handler that skips charging and an undo that simply
   resets the clock. Add a scripted result or equivalent deterministic
   fixture through the GUI turn path. Check the next allocation after a
   charge, refund only the last exchange after at least two charged
   turns, and exercise the lone-move shortcut without starting search.
   The GUI currently measures from worker launch to result polling.
   Define which duration the play clock charges so delayed UI polling
   cannot accidentally spend the engine's search budget.

Specify what interactive play does on a clock overrun. The design
defines return-and-forfeit for the match harness. The proposed play
loop keeps applying moves with a zero remainder, which still receives
the allocator's 1 ms minimum. A test should pin whichever interactive
behavior is intended.

I read the SKIS issue and approved clock design, reproduced
`play_agent_policy`'s intended failure (flat limits against variant 3),
and ran formatting checks for the engine and GUI. The submitted diff
passed the whitespace check. The GUI RED binaries and full suite were
not run for this tests-first review.

## RED re-review of `834c945` (test changes in `2d62a21`)

**Request changes.** The GUI result-handler, reduced allocation,
partial undo and lone-move cases address the earlier coverage gap.
The definitions for worker-side timing and interactive overrun are
clear. Two CLI test details remain:

1. **Major — Assert the clock update precedes the move.** The
   `Recorder` in `tests/cli.rs` records only calls to `clock`, and
   its `choose` ignores the recorded value. Calling `choose`
   before `clock` on every turn would pass `play_turn_clock`,
   yet the first move would use flat limits and the next move would
   use the old clock. Record the value observed by each `choose`,
   or assert the ordered clock and choose calls. The pass fixture
   can then also prove that neither method was called.
2. **Minor — Remove the subprocess timing assertion.**
   `play_opponent_is_search` still requires the executable to return
   in 51 seconds. The clock measures the engine's work under the
   documented overrun rule. Keep the exit status and legal-reply
   assertions as the smoke test.
