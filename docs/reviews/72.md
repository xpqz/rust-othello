# Review: Issue 72 — Implement minimal evaluation in centidiscs (RED)

Verdict: **request changes**

## Verified

- #71 was merged and closed. This branch is based on the current `main`.
  `cargo fmt --check` passes, and `tests/eval.rs` fails only with the
  expected E0432.
- Checked against the DESIGN.md table: a1 200, b1 80, b2 50, c1 110, d1 105,
  c2 98, the start position 0, and the mixed case 240 (200 − (−40), disc
  diff 0).
- The full-board overflow input sums to 6512: table 112 (corners +400, C
  −160, X −200, A-edges +80, B-edges +40, inner ring −48) plus 6400 for the
  discs. It is just over `EVAL_BOUND`, which makes it a good bound test.

## Required

1. **The `d2` expectation is wrong.** `at(3, 1)` is d2, which is on rank 2.
   In the DESIGN.md table, rank 2 reads `-20 -50 -2 -2 -2 -2 -50 -20`, so d2
   is −2 and the expected value is **98**, not 99. Only ranks 3–6, files c–f,
   hold −1. As written, the test forces an implementation to use a table
   that differs from the documented one. Fix it to 98, and add one true −1
   square so that value is pinned: c3 (`at(2, 2)`) → 99.

## Minor

2. **Static or dynamic X/C values.** PLAN.md's feature contract says to
   "replace the design table's static X/C values with a neutral base value …
   and apply the X/C penalty only while the adjacent corner is empty". This
   PR uses the static design table (b1 −20, b2 −50). That is defensible for
   the Phase 2 minimal evaluator, since corner risk is a Phase 7 feature and
   this function becomes the frozen baseline that Phase 7 must beat. But
   PLAN.md doesn't say so explicitly. State in the intended-behaviour notes
   that Phase 2 deliberately keeps static X/C values and that dynamic corner
   risk lands in Phase 7 (#96). Otherwise a later reader will see this as a
   violation of the contract.

3. **The debug assertion can fire on a reachable position.** The 64–0 full
   board is a legal terminal position and evaluates to 6512. Search never
   evaluates terminals (they are resolved before the cutoff), but the
   `antisymmetry_and_bounds` playouts do visit terminals. A seed that reaches
   a 64–0 wipeout would panic in debug. That is improbable but not
   impossible. Either document "`evaluate` is for non-terminal positions;
   terminals use `terminal_score`" and skip terminals in that test, or accept
   the clamp path there. Non-terminal positions stay below about 6,300, so
   the bound is safe in normal use.

4. **The `fn(Board) -> i32` claim.** Pin it in a test, as was done in
   `score_types`: `let _: fn(Board) -> i32 = evaluate;`. #73's `SearchConfig`
   depends on that exact signature.

# Re-review (round 3, GREEN)

Verdict: **request changes** (small)

## Verified

- The tests are unchanged since the RED approval. `./scripts/check.sh` passes,
  and `eval` is 6/6 in both debug and release. The engine is 179 lines.
- `WEIGHTS` matches the DESIGN.md table row by row. I checked all 64 values.
  `evaluate` is antisymmetric, uses `SCORE_SCALE` for the disc term, and has
  the debug assertion and release clamp exactly as specified.

## Required

1. **rustfmt has flattened the table into an unreadable run.** The 8×8 shape
   was the only way to check the table by eye. Now the rows wrap at
   arbitrary points (`… -1, -1,` / `-2, 10, 5, …`), and a misplaced value,
   or a transposition when Phase 7 edits it, would be invisible. This
   function is also the frozen baseline that gets copied into tools. Use
   `[[i32; 8]; 8]`. rustfmt keeps each short row on its own line, so no
   `#[rustfmt::skip]` is needed. Enumerate with `WEIGHTS.as_flattened()`.
   That costs about 7 lines and keeps `eval.rs` well inside budget.

## Nits (non-blocking)

- The module doc repeats the heuristic-outranks-proven-win note, which #62
  and #63 placed in `score`. Refer to `crate::score` instead of restating
  it.
- The non-terminal contract ("terminals use `terminal_score`") is in the PR
  notes but not on `evaluate`'s doc comment, which is where #73's author will
  look.
