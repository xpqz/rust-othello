# Issue 161: Engine clock allocation

Engine side of `docs/design/time.md` (approved, revision 3): § Engine and
§ Tests › Engine.

## RED

### Scaffolding, so that the tree compiles

- `SearchLimits.start_ms`, documented as "no iteration starts after this
  many ms; the exact solve ignores it". `new` and `depth` set it to
  `time_ms`. Search does not read it yet.
- `pub const MAX_CLOCK_MS: u64 = 1 << 40` and a stub
  `allot(board, remaining_ms, threshold)` that returns
  `SearchLimits::new(64, remaining_ms, 0)`.
- `Agent::clock(&mut self, _remaining_ms: u64) {}`, a default no-op.
- `SearchAgent::limits(&self, board)` returns the stored limits.
  `clock_agent(config, limits)` is a stub that builds a plain
  `search_agent`.
- The 10 full `SearchLimits { … }` literals in `tests/search.rs` gain a
  `start_ms` equal to their `time_ms`.

### Tests: `tests/clock.rs` (15)

Fixtures:

- `line(e)`: lowest-square plies from the start until `e` empties remain
  and the mover has a legal move.
- `split()`: the first seeded random 16-empty position where the frozen
  limits (time 0, start 0) make the agent fall back to a depth-8 search
  whose move is strictly worse than the exact optimum. The fallback move is
  computed with a fresh `MAX_ENTRIES` table, as in a new agent.

| Test | Checks | Against the stubs |
|---|---|---|
| `flat_start_equal` | `new` and `depth` give `start_ms == time_ms` | passes |
| `deadline_aborts_search` | `time_ms` 50, `start_ms` unlimited, depth 64 at 40 empties: returns within 30 s, aborted below 64 | passes (guard) |
| `start_stops_admission` | `start_ms` 50, `time_ms` unlimited: returns within 60 s, and its nodes, move and score equal a plain `depth(d)` search, so the last iteration completed | fails (60 s timeout) |
| `start_zero_fallback` | `start_ms` 0: depth 0 | fails |
| `exact_ignores_start` | `start_ms` 0 in a 10-empty solve: still solved | passes (guard) |
| `allot_exact` | `e ≤ T`: `start = time = max(1, R/8)` for R 16,000, 15, 7, 0; R 15 gives a deadline of 4 ms ≤ R/2 | fails |
| `allot_examples` | design table: e 60 R 52 s → 2,080/4,160; e 40 R 35 s → 3,500/7,000; e 19 R 1 s → 250/250 | fails |
| `allot_bounds` | e 19, 30, 44, 45, 60 over 201 values of R: `1 ≤ start ≤ time ≤ max(1, R/4)`, both non-decreasing in R | fails |
| `allot_weight` | m = 13 both ways: e 44 (T 18) and e 45 (T 19) give 3,000 and 2,000 | fails |
| `allot_tiny` | R 0, 1, 3 give 1/1 in both branches | fails |
| `allot_clamped` | `u64::MAX` equals `MAX_CLOCK_MS` in both branches | fails |
| `clock_ignored_flat` | `search_agent` limits unchanged after `clock` | passes |
| `clock_limits_follow` | `clock_agent` on a 30-empty heuristic position: fixed limits first, then `allot` for `clock(40 s)`, then for `clock(20 s)`, and the two differ | fails |
| `clock_choose_uses` | on `split()`, `choose` plays the fallback move before the clock; after `clock(10^8)`, `limits` equals `allot` and `choose` plays a move of optimal exact value | fails |
| `clock_book_hit` | a clocked agent with `book: true` plays the book move at the start | passes (guard) |

**How the start-limit tests separate the two checks:** each sets one
limit to unlimited. If the admission check read `time_ms`,
`start_stops_admission` would run to depth 64 at 40 empties and fail on
its timeout. If the in-search check read `start_ms`,
`deadline_aborts_search` would do the same. Neither depends on where the
1,024-node polls fall.

**Expected failures:** 10, all in `tests/clock.rs`, all from the stubs.
`start_stops_admission` fails by its 60 s timeout. The other 5 pass now
and guard behaviour that must not change.

### Results

- `cargo test --release --no-fail-fast`: engine 201 passed, 10 failed (as
  listed). tools 72, trainer 124 and gui 10 pass.
- Clippy (`-D warnings`) is clean on all four crates, and rustfmt is
  applied.
- Engine budget: 1,312 of 1,500 lines, with the stubs.

### GREEN plan

- Iterative deepening compares the start instant plus `start_ms` before
  each iteration. `Ctx` keeps the `time_ms` deadline for the in-search
  check. The exact branch is unchanged.
- `allot` as specified, with `R` clamped to `MAX_CLOCK_MS`.
- `SearchAgent` stores an optional remaining clock, which `clock_agent`
  enables. `limits` computes `allot` when it is set, and `choose` uses
  `limits`.

## RED review response

- **Runaway search (major):** `bounded` now runs each case in a child copy
  of the test binary. It calls `current_exe` with
  `--exact child_search --ignored --nocapture` and selects the case with
  `CLOCK_CASE`. It polls `try_wait`, and on timeout calls `kill` and then
  `wait`, so the search ends with its test. `child_search` is an
  `#[ignore]`d test that does nothing without `CLOCK_CASE`, and it prints
  `result depth nodes best score`. The two cases stay independent
  (`deadline`, `admission`), and the admission case still fails against
  the stubs.
- **Cleanup verified:**
  - against the stubs, `cargo test --release --test clock` gives
    5 passed, 10 failed and 1 ignored (`child_search`);
  - `start_stops_admission` fails at its 60 s timeout;
  - `pgrep -fl child_search` afterwards finds no process. A child that had
    not been killed would have outlived the test process as an orphan.
- **Fixture bound:** `split()` searches seeds 0..1000 and panics with a
  message if none qualifies. It still requires the fallback move to be
  strictly worse than the exact optimum.
- **Book hit:** `clock_book_hit` uses an evaluator that panics if called,
  so the clocked book hit is shown to bypass search. It passes against the
  stubs, as `book::play` already answers first.
