## Step 1 RED: null-window search

Intended behaviour: in `negamax` and `root`, the first move is searched
with the full window and each later move with `(alpha, alpha + 1)`; a
value strictly inside `(alpha, beta)` is searched again with the full
window. Midgame and exact search alike. Values returned at fixed depth
do not change; node counts fall.

Tests written:

- `tests/search.rs::window_equivalence` (new). On positions from random
  playouts (fixed seed, every seventh position with a legal move), with
  a pseudo-random evaluation (`noise`, a hash of the position, −2,000 to
  2,000) so that scores rarely tie and windows matter:
  - 1,000 positions with more than 8 empties: `negamax`, `search`,
    `search_limited` and `search_tt` (cold 65,536-entry table) each
    return the value of plain `minimax` (no ordering, no windows, no
    table) at the same depth;
  - 200 positions with 8 or fewer empties (`endgame_threshold: 8`):
    `search_limited` and `search_tt` return the exhaustive value;
  - in both groups the move `search_tt` returns is checked by searching
    its child with `minimax`: it must be worth the root value.

  Depths: 980 positions cycle through 1 to 4 and every fiftieth (20
  positions) is at depth 5. The issue asked for depths 1 to 5 evenly;
  that took 62 s in a debug build, this takes 15 s. Say if the even
  spread is wanted and I will make the test release-only instead.
  The test passes on the current engine by design: it pins what must
  not move. In GREEN I will show it fails when the re-search is left
  out.
- `tools/tests/golden.rs::fewer_nodes` (new). The standard engine at
  depth 8 over the 23 corpus boards must use at most 80% of the
  3,791,452 nodes it uses today (`FULL_WINDOW_NODES`, the sum of
  `GOLDEN_V2`'s node column). The spike measured 69% on the depth-10
  midgame workload.

Expected failures now: `fewer_nodes` fails ("3791452 nodes").
`window_equivalence`, `golden_v1` and `golden_v2` pass.

Expected in GREEN: `golden_v1` and `golden_v2` fail on their node
columns only. I will re-record the node columns and show from the diff

## Step 2 RED: table move from shallower searches

Intended behaviour: in midgame search, the move stored in a heuristic
table entry for the position is tried first whatever depth the entry
was searched to. Today `Entry::move_hint(depth)` returns it only when
the entry's depth is at least the current depth, so with iterative
deepening the previous iteration's move is ignored below the root.
Endgame entries still give no hint here (exact search is step 4). An
entry with no move gives none. Values at fixed depth do not change.

History: the restriction dates from #87 ("a deeper heuristic entry
supplies a move for ordering at a shallower depth, not the reverse").
I found no measurement behind it in the notes or reviews of #87 or #88.

Tests written:

- `tests/tt.rs::order_hints` (changed). A depth-4 heuristic entry with
  move 7 now must give `Some(7)` when asked at depth 5 as well as at
  depth 3; with `mv = NO_MOVE` it gives `None`; the endgame entry still
  gives `None`.
- `tools/tests/golden.rs::fewer_nodes` (changed). A second condition:
  depth-8 nodes over the corpus at most 85% of `NULL_WINDOW_NODES`
  (2,970,325, step 1's total). The 80%-of-full-window condition and
  `FULL_WINDOW_NODES` stay.
- Unchanged and binding: `corpus_depths`, `golden_v1`,
  `window_equivalence`, `window_bounds`, `tt_equivalence`,
  `tt_sample_equivalence`, `tt_deep_then_shallow`.

Expected failures now: `order_hints` ("left: None, right: Some(7)");
`fewer_nodes` ("2970325 nodes"). Everything else passes
(`cargo test --test tt`: 7 passed, 1 failed; release golden: 4 passed,
1 failed).

Planned in GREEN, said now so it is not a surprise: once the depth no
longer matters, `move_hint`'s `depth` parameter is dead, and I intend
to remove it. That changes the three call lines in `order_hints` (the
argument goes; the expected values stay) and the one call in
`negamax`. `GOLDEN_V2`'s node column will be re-recorded again, with
the same no-move-or-score-changed check.

Before: step 1's run 7 (`docs/tuning/speed_135_bench_step1_run7.log`),
