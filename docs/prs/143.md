## Step 2: generated code and microbenchmark

Disassembly of the release build (fat LTO), from the scratch copy:

- `features`: the 48-lane accumulation is vectorised: per row, six
  128-bit loads and adds for each side's `ROWS` entry. Overheads per row
  are two `LazyLock` initialisation checks (`ldapr`) and two bounds checks.
- `evaluate`: 46 bounds-checked scattered `i16` reads from the 334 KB
  stage slice of `TABLE`.

Microbenchmark (scratch `examples/micro.rs`, copied to
`docs/tuning/eval_micro_143.rs.txt`): 2^20 boards from random playouts
of the corpus positions ("varied") against 16 boards repeated ("hot"),
five passes each; the machine was shared with review checks, so the
figures are within about ±3 ns:

| | varied | hot |
|---|---|---|
| `features` | 21–23 ns | 21–25 ns |
| `evaluate` (including `features`) | 50–58 ns | 38–41 ns |

- `features` costs the same with its table hot or cold: it is not
  memory-bound. 96 vector loads and about 140 vector adds per call put its
  throughput floor near 35–40 cycles; it runs at about 70.
- Two cheap rewrites were tried in scratch and rejected: separate sums for
  the two sides (no change) and hoisting the `ROWS` reference out of the
  loop (slower, 28 ns).
- `evaluate`'s weight reads cost about 12 ns more on varied boards: cache
  misses on data-dependent indices, roughly a tenth of search time, which
  table reordering cannot remove.

Conclusion: node cost in evaluation is near its practical floor; the next
gains are from searching fewer nodes (ProbCut v2, next epic).
