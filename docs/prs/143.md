## Step 2: generated code and microbenchmark

Disassembly of the release build (fat LTO), from the scratch copy:

- `features`: the 48-lane accumulation is vectorised: per row, six
  128-bit loads and adds for each side's `ROWS` entry. Overheads per row
  are two `LazyLock` initialisation checks (`ldapr`) and two bounds checks.
- `evaluate`: 46 bounds-checked scattered `i16` reads from the 334 KB
  stage slice of `TABLE`.

Microbenchmark (scratch `examples/micro.rs`, copied to
`docs/tuning/eval_micro_143.rs.txt`): 2^20 boards from random playouts
of the corpus positions ("varied") against 16 boards repeated ("hot"),
five passes each; the machine was shared with review checks, so the
figures are within about ±3 ns:

| | varied | hot |
|---|---|---|
| `features` | 21–23 ns | 21–25 ns |
| `evaluate` (including `features`) | 50–58 ns | 38–41 ns |

- `features` costs the same with its table hot or cold: it is not
  memory-bound. 96 vector loads and about 140 vector adds per call put its
  throughput floor near 35–40 cycles; it runs at about 70.
- Two cheap rewrites were tried in scratch and rejected: separate sums for
  the two sides (no change) and hoisting the `ROWS` reference out of the
  loop (slower, 28 ns).
- `evaluate`'s weight reads cost about 12 ns more on varied boards: cache
  misses on data-dependent indices, roughly a tenth of search time, which
  table reordering cannot remove.

Conclusion: node cost in evaluation is near its practical floor; the next
gains are from searching fewer nodes (ProbCut v2, next epic).

## Review response (review of `715742f`)

### Conclusions narrowed

The step 2 conclusions claimed more than the experiment shows. Withdrawn:
that `features` "is not memory-bound", that it runs at about twice a
"throughput floor near 35–40 cycles", that the slower varied-board
`evaluate` is "cache misses ... which table reordering cannot remove", and
that evaluation node cost is "near its practical floor". No cache flush,
miss or stall counter was measured, and the cycle figure was an
instruction count, not a measured bound.

What the measurements support:

- The conditions are a **varied working set** (2^20 playout boards) and a
  **repeated subset** (16 boards), not cold and hot caches. `features` took
  about the same time in both (observed 21–30 ns across runs);
  `evaluate` was slower on the varied set (observed 50–63 ns against
  38–48 ns). These are observed ranges from runs on a shared machine, not
  an uncertainty bound.
- In the generated code the accumulation in `features` is vectorised, with
  two `LazyLock` checks and two bounds checks per row; `evaluate` makes 46
  bounds-checked table reads.
- Two small rewrites of `features` (separate sums per side; hoisting the
  table reference) gave no improvement in these runs; the hoisted version
  was slower.
- Chosen next direction: searching fewer nodes (ProbCut v2, #144). This
  is a choice, not a demonstration that evaluation gains are exhausted.

`search_bench`: the fixed split restores the workload's membership; timings
compare across logs only with matching build profile and engine/
configuration provenance (the tools profile changed at #134, see
`docs/PLAN.md` § Build profile).
