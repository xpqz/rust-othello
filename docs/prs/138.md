## Step 1 RED: decoded weights

A pure speed change; no test fails today.

Intended change: `pattern::evaluate` reads each weight as two bytes
from the `include_bytes!` data with two bounds checks. Decode the file
once into a table of `i16` and read from the slice for the position's
stage. Same values, so same evaluations, scores and node counts. Cost:
the decoded copy, 2,007,180 × 2 bytes = 4.0 MB of heap, built on first
use.

Tests:

- `tests/pattern.rs::evaluate_wide` (new): on every position of random
  playouts until 100,000 have been checked, `evaluate` must equal the
  clamped sum of the weights read straight from the file's bytes
  (`reference`, already in the test file and independent of the
  engine's reading code). It also requires more than 1,000 positions
  in each of the 12 stages, so every stage's part of the table is
  read. The issue first asked for a slot-by-slot check of the decoded
  table; the table is private, so the check is made through
  `evaluate`, and SKIS #138 now says so.
- Unchanged and binding: `evaluate_reference`, `evaluate_layout`,
  `evaluate_bound`, `evaluate_clamp`, `asset_length`; `golden_v2` with
  per-position node counts, `corpus_depths`, `golden_v1`.

Results now: `cargo test --test pattern`: 15 passed, `evaluate_wide`
among them by design. Engine fmt and clippy clean.

In GREEN: a mutation (one stage's slice off by one slot) must make
`evaluate_wide` fail.

Before: measured alongside the after-runs, alternating binaries, as
#137 settled on.

## Benchmark correction: table clearing was counted as exact-search time

Found while measuring step 1. Forty alternating pairs with the
benchmark as it was (`docs/tuning/speed_138_bench_step1_paired_e{0,1}_{1..40}.log`)
all showed the midgame workload about 1.10 times faster, 21 of them
with both midgame spreads inside 3%, and **not one** with both exact
spreads inside 3%, on code that exact search does not run.

Cause: `search_bench` clears the 64 MiB table before every search and
counted that in the elapsed time. The exact workload is 800 solves of
about half a millisecond each, so it also did 800 clears. Timed
apart: about 360 to 395 ms of clearing in an exact round of about 745
to 780 ms, against 5 ms in a midgame round of about 1,040 ms. Clearing
is memory traffic and moves with whatever else the machine is doing;
that is where the exact workload's spread came from all day.

Change (`tools/examples/search_bench.rs`, tools only): each search is
timed from after the clear; the clear is timed apart and printed per
round (`clear ms <midgame> <exact>`); the header line says `bench v2`.
Workload, node counts and output columns are otherwise unchanged. The
table is still cleared before every search, so searches are as cold as
before. Tools fmt and clippy clean; tools budget unchanged.

What this means for figures already reported, all of which stand as
measured but measured something wider than search:

- Midgame figures are unaffected (5 ms in over a second).
- Every exact-workload time in #133, #135 and #137 includes about
  360 to 400 ms of clearing on both sides of each comparison. The
  ratios therefore **understate** the change in search time. For
  example #137's accumulated exact figure, 989.9 → 746.5 ms (1.33),
  is roughly 610 → 370 ms of search (about 1.65) if 380 ms of clearing
  is taken from both; I have not re-measured the older engines and
  give that only as arithmetic.
- Exact-workload spreads in those issues were partly clearing noise.
  Steps were never kept on the strength of a spread that failed, so no
  decision changes; some were delayed by it.
- In play the table is cleared once per game, not per solve, so the
  clearing cost in the old numbers has no counterpart in a real game.

From here on, times in this issue are `bench v2` search times.

## Step 1 GREEN: decoded weights

Done before the RED review, as stated at the top.

What changed:

- `src/pattern.rs`: `static TABLE: LazyLock<Vec<i16>>`, the file's
  little-endian pairs decoded once (`as_chunks::<2>`); `evaluate` takes
  the stage's slice, `TABLE[stage * TABLE_SLOTS..][..TABLE_SLOTS]`, and
  adds `table[feature]` for each feature. `WEIGHTS` stays as the
  embedded file. One bounds check per weight in place of two, and a
  16-bit load in place of two byte loads.
- Memory: 4.0 MB of heap for the decoded copy, built on the first
  evaluation; the embedded 4.0 MB file remains in the binary.
- Engine lines 1,054 → 1,058 (+4).

Tests: `tests/pattern.rs` 15 passed. Mutation: with stage 7's slice
starting one slot late, `evaluate_wide` and `evaluate_reference` fail.
`./scripts/check.sh`: passes (engine 1,058, tools 1,278, trainer
1,150), `golden_v2`'s per-position node counts unchanged. Benchmark
node totals 8,556,688 and 7,001,000 in every run.

Measurement, `bench v2`, alternating binaries of the start of the
issue (`55716d8` engine sources with the corrected benchmark) and of
step 1, eight pairs (`docs/tuning/speed_138_bench2_step1_paired_e{0,1}_{1..8}.log`),
load about 2. Three pairs have both runs within 3% on both workloads:

| Pair | Midgame start → step 1, min ms | Ratio | Slowest after / fastest before | Exact start → step 1, min ms |
|---|---|---|---|---|
| 4 | 1,153.0 → 1,044.0 | 1.104 | 1,054.9 / 1,153.0 | 382.8 → 383.8 |
| 5 | 1,144.5 → 1,051.7 | 1.088 | 1,066.5 / 1,144.5 | 384.9 → 385.3 |
| 8 | 1,107.0 → 1,007.9 | 1.098 | 1,017.0 / 1,107.0 | 384.3 → 384.6 |

Against the registered conditions: midgame at least 5% faster, met in
each (1.09 to 1.10); slowest after-round under fastest before-round,
met in each; exact not more than 3% slower, met (unchanged, as it must
be: exact search does not evaluate). **The step is kept.** The other
five pairs fail a spread condition and do not count; the step 1
binary's midgame minimum is the lower in all eight, as it was in all
forty of the earlier pairs.

Asked by the user during this step: would an 8-bit weight table help
cache locality? Measured and recorded in the issue: no. 8.4% of the
weights exceed ±127, so it would be lossy, and an 8-bit table timed
the same as the 16-bit one.

Claims checked against the tree: `TABLE` in `src/pattern.rs`;
`evaluate_wide` in `tests/pattern.rs`; `bench v2` in
`tools/examples/search_bench.rs`.

## Step 2 RED: padded sums

Intended change: inside `pattern.rs` the row table and the running
sums in `features` become 48 lanes wide instead of 46; lanes 46 and 47
are always zero. The sums are then six whole 8-lane vector steps with
no scalar remainder. `INSTANCE_COUNT`, the return type of `features`
and everything public are unchanged.

No new test, as for #137's step 2: `features_wide` (100,026 boards
against the one-square-at-a-time reference) and `features_reference`
pin every one of the 46 outputs; `evaluate_wide`, `golden_v2` with
node counts, `corpus_depths` and `golden_v1` pin what follows from
them. All pass today by design. In GREEN: a mutation that lets a
padding lane leak into lane 45 must fail `features_wide`.

Before: the step 1 binary, alternating, `bench v2`.
