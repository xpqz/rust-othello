## Step 1 RED: decoded weights

A pure speed change; no test fails today.

Intended change: `pattern::evaluate` reads each weight as two bytes
from the `include_bytes!` data with two bounds checks. Decode the file
once into a table of `i16` and read from the slice for the position's
stage. Same values, so same evaluations, scores and node counts. Cost:
the decoded copy, 2,007,180 × 2 bytes = 4.0 MB of heap, built on first
use.

Tests:

- `tests/pattern.rs::evaluate_wide` (new): on every position of random
  playouts until 100,000 have been checked, `evaluate` must equal the
  clamped sum of the weights read straight from the file's bytes
  (`reference`, already in the test file and independent of the
  engine's reading code). It also requires more than 1,000 positions
  in each of the 12 stages, so every stage's part of the table is
  read. The issue first asked for a slot-by-slot check of the decoded
  table; the table is private, so the check is made through
  `evaluate`, and SKIS #138 now says so.
- Unchanged and binding: `evaluate_reference`, `evaluate_layout`,
  `evaluate_bound`, `evaluate_clamp`, `asset_length`; `golden_v2` with
  per-position node counts, `corpus_depths`, `golden_v1`.

Results now: `cargo test --test pattern`: 15 passed, `evaluate_wide`
among them by design. Engine fmt and clippy clean.

In GREEN: a mutation (one stage's slice off by one slot) must make
`evaluate_wide` fail.

## Benchmark correction: table clearing was counted as exact-search time

Found while measuring step 1. Forty alternating pairs with the
benchmark as it was (`docs/tuning/speed_138_bench_step1_paired_e{0,1}_{1..40}.log`)
all showed the midgame workload about 1.10 times faster, 21 of them
with both midgame spreads inside 3%, and **not one** with both exact
spreads inside 3%, on code that exact search does not run.

Cause: `search_bench` clears the 64 MiB table before every search and
counted that in the elapsed time. The exact workload is 800 solves of
about half a millisecond each, so it also did 800 clears. Timed
apart: about 360 to 395 ms of clearing in an exact round of about 745
to 780 ms, against 5 ms in a midgame round of about 1,040 ms. Clearing
is memory traffic and moves with whatever else the machine is doing;
that is where the exact workload's spread came from all day.

Change (`tools/examples/search_bench.rs`, tools only): each search is
timed from after the clear; the clear is timed apart and printed per
round (`clear ms <midgame> <exact>`); the header line says `bench v2`.
Workload, node counts and output columns are otherwise unchanged. The
table is still cleared before every search, so searches are as cold as
before. Tools fmt and clippy clean; tools budget unchanged.

What this means for figures already reported, all of which stand as
measured but measured something wider than search:

- Midgame figures are unaffected (5 ms in over a second).
- Every exact-workload time in #133, #135 and #137 includes about
  360 to 400 ms of clearing on both sides of each comparison. The
  ratios therefore **understate** the change in search time. For
  example #137's accumulated exact figure, 989.9 → 746.5 ms (1.33),
  is roughly 610 → 370 ms of search (about 1.65) if 380 ms of clearing
  is taken from both; I have not re-measured the older engines and
  give that only as arithmetic.
- Exact-workload spreads in those issues were partly clearing noise.
  Steps were never kept on the strength of a spread that failed, so no
  decision changes; some were delayed by it.
- In play the table is cleared once per game, not per solve, so the
  clearing cost in the old numbers has no counterpart in a real game.

From here on, times in this issue are `bench v2` search times.

## Step 2 RED: padded sums

Intended change: inside `pattern.rs` the row table and the running
sums in `features` become 48 lanes wide instead of 46; lanes 46 and 47
are always zero. The sums are then six whole 8-lane vector steps with
no scalar remainder. `INSTANCE_COUNT`, the return type of `features`
and everything public are unchanged.

No new test, as for #137's step 2: `features_wide` (100,026 boards
against the one-square-at-a-time reference) and `features_reference`
pin every one of the 46 outputs; `evaluate_wide`, `golden_v2` with
node counts, `corpus_depths` and `golden_v1` pin what follows from
them. All pass today by design. In GREEN: a mutation that lets a
padding lane leak into lane 45 must fail `features_wide`.

Before: the step 1 binary, alternating, `bench v2`.

## Step 3: incremental indices, prototype measured — slower; not recommended

Measurement only, in a scratch copy of the step 2 engine; nothing from
it is in this branch. The prototype is kept, untracked, as
`scratch/order-spike/incremental_prototype.patch` in the main checkout.

Design tried, the cheapest one I could find that leaves the evaluator
interface alone: a midgame node with one ply left computes two sets of
index sums once, for the mover's discs and for the opponent's
(`sums`, the same row table, 16 row additions). Each leaf below it is
then evaluated from those sums and the difference between the two
boards (`evaluate_child`): swap the two sets, add the placed square's
contribution to one, move each flipped square's contribution from one
to the other (a 64-entry per-square table), combine as mover + 2 ×
opponent, add the offsets and read the 46 weights. A leaf that is not
a direct child of the remembered node (after a pass) falls back to the
full evaluation; other evaluators always do. 74 added engine lines.

Correctness: `search_bench` node totals identical (8,556,688 and
7,001,000), and the release golden suite passes on the prototype
(`corpus_depths`, `golden_v1`, `golden_v2` with node counts).

Timing, `bench v2`, alternating with the step 2 binary, load about 2,
none of it gate-quality (most spreads over 3%):

| Variant | Midgame min ms, runs | Step 2 alongside |
|---|---|---|
| First form | 1,238 to 1,267 (six runs) | 995 to 1,020 |
| Sums computed only after a table miss; plain indexed loops | 1,275 to 1,281 (three runs) | 1,001 to 1,050 |

**About 25% slower in both forms.** A five-second sample of the second
form (`sample`, functions out of line) has `evaluate_child` at 877
samples for about 5.6 million leaf calls and `sums` at 488 for about
1.8 million parent calls: per call, the incremental leaf evaluation
costs about what the full evaluation costs now, and the parent's sums
come on top.

Why, as far as this shows: after #133 the full index computation is
already only 16 additions of 48-lane rows, and after steps 1 and 2 of
this issue the whole evaluation is about 40 ns. An incremental leaf
needs a 192-byte copy, about 1 + 2 × flips row additions, a combine,
and the same 46 weight reads, so there was little to save, and the
bookkeeping cost more than it saved. I did not hand-tune further or
inspect the generated code; a better-vectorised `sums` and
`evaluate_child` would narrow the gap. I do not see it turning a 25%
loss into a gain worth 74 lines and a second evaluation path.

Recommendation: do not pursue incremental indices for this evaluator.
What is left in the evaluation is the 46 weight reads and the index
arithmetic, both already near their floor; the next gains are more
likely in the board functions (about a quarter of the profile) or in
searching fewer nodes.

### What the earlier step 3 figures were, and their limits

The nine timing runs reported above were made with builds that had no
`#[inline(never)]`; I added those attributes afterwards, for the
sample only, and then saved the patch from the annotated tree. So the
saved patch was the sampled variant, not the timed one, and no per-run
logs of the timing were kept. That record cannot be audited, and I do
not ask anyone to rely on it. The untracked
`scratch/order-spike/incremental_prototype.patch` is that annotated
variant and is superseded by the committed files below.

### Conclusions, narrowed

- Supported: this prototype, in this form, built natively, is about
  25% slower than step 2 on the midgame workload with identical node
  counts, and costs about 80 lines. It is not merged.
- Withdrawn: that "per call, the incremental leaf evaluation costs
  about what the full evaluation costs". That was read off an
  instrumented sample and call counts taken from a different run.
- Withdrawn: that the weight reads and index arithmetic are "near
  their floor", and that incremental indices cannot help this
  evaluator. Neither was measured. A different design (sums carried
  down the whole search, or a prototype whose generated code has been
  inspected and tuned) is untested. My recommendation not to pursue it
  now stands as a judgement about where to spend effort next, not as a
  result.

### Smaller points from the review

- Memory, completed: besides the 4.0 MB decoded table, the padded row
  table is 8 KiB larger (2,048 rows × 2 lanes × 2 bytes) and each sums
  array 4 bytes.
- "Exact search does not evaluate" was too broad. The recursive exact
  search evaluates nothing, but `search_tt` evaluates the root once
  per search for its fallback result, so the exact workload makes 800
  evaluations a round against millions in the midgame workload.
- Historical exact figures: the arithmetic I gave for #137 (taking
  380 ms of clearing from both sides) is not a measurement and I
  withdraw it as a figure. What can be said: the old benchmark's exact
  times were end-to-end times of a cold-table workload including
  clearing; whether and how much that diluted a given old ratio
  depends on the clearing cost in those particular runs, which was not
  recorded.

### Proposal for the next step (not implemented here)

1. Board functions, 32.9%. `runs` alone is 22.7%. Every node calls
   `legal_moves` on entry, leaves included, where it only decides
   between "evaluate" and "pass or game over"; and at depth 2 and 3
   `ordered_moves` plays every move and generates the replies to count
   them. First measurements to take: how the `runs` calls divide
   between those callers, and what a cheaper pass test at leaves or a
   cheaper reply count would be worth. Hypotheses, not results.

   is a strength question, not a speed one, and belongs with #136's
