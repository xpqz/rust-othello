## Step 1 RED: the last empty square

Intended behaviour: an exact node whose position has one empty square
returns the exact result directly: the mover plays the square if that
flips anything; otherwise the opponent does if that flips anything;
otherwise the game is over and the score is the final one with the
empty square awarded to the winner. No child call, no move generation,
no table probe or store. The value returned is the exact value
whatever window was passed, which satisfies the fail-soft contract.

Node accounting changes with it: the node that meets the last square
is counted, and nothing below it is. Today the same position costs 2
nodes when the mover can play, 3 when the mover passes and the opponent
plays, and 1 when nobody can. So `SearchResult::nodes` and `max_nodes`
count fewer nodes for the same exact search; results are unchanged.

Tests:

- `tests/search.rs::last_square` (new). 10,000 positions with one
  empty square (`one_empty`): the 1-empty position of each of 2,500
  random games, plus three recolourings of it (each disc the mover's
  with probability 1/2, 1/8 and 7/8), so that all three cases are
  common: mover plays 7,739, mover passes and the opponent plays 1,881,
  nobody can play 380; the test requires more than 300 of each. For
  each position and for four windows (full, `(v−1, v)`, `(v, v+1)`,
  `(−100, 100)`), `solve` must return the exhaustive reference value
  `exact(board)` and `ctx.nodes` must be 1. **Fails today** on the node
  count ("left: 2, right: 1"); with that assertion removed the rest of
  the test passes on the current engine, which I checked.
- Unchanged and binding: `window_equivalence` (200 exhaustive
  endgames), the solver tests in `tests/search.rs` (`solve_sample`,
  `solve_wdl`, pass and terminal cases, `solver_reuses_endgame_bounds`),
  `corpus_depths`, `golden_v1`, `golden_v2`'s moves and scores.
- Expected in GREEN: `golden_v2`'s node column changes for the eight

  The node-limit tests (`node_limit_partial`, `node_limit_fallback`,

  or tiny limits; I will run them and report whether any assertion

- `exact_bench` prints each position's move and score; GREEN must

## Step 1 GREEN: the last empty square

What changed (`src/search.rs`):

- `last_square(board) -> i32` (new, private): the square is the one
  bit not set in either side. `flips` is computed for the mover and for
  the opponent on that square. If the mover's is non-zero the result is
  `final_score` of the full board after the mover plays; else if the
  opponent's is non-zero, minus `final_score` of the full board after
  the opponent plays (from the opponent's side); else `final_score` of

  It returns WTHOR discs; the caller applies `terminal_score`, as every
  other terminal does.

  has no `legal_moves`, no child call and no table access; `flips` and
  `final_score` are its only calls. The node-limit and deadline checks

## Step 2 RED: the last two empty squares

Re-review of `c8eb863` approved step 1.

Intended behaviour: an exact node whose position has two empty squares
is settled in that node. The mover tries each empty square that flips
something; the remaining square is settled by `last_square` for the
other side. If the mover can play neither, the opponent tries both in
the same way; if neither side can play, the game is over. No child
call, no move generation, no table. Unlike the one-square routine this
one searches (two alternatives), so it takes the window: it stops when
a move reaches beta, and its result is the exact value when that lies
inside the window and a true bound otherwise, the same fail-soft
contract as `negamax`.

It gives up the table at two empties, where today about 11% of probes
cut off. Scratch trial of the idea on top of step 1 (`exact_bench`, one
run each, not gate evidence): 16 empties 5,984 → 5,382 ms, 14 empties
1,857 → 1,647 ms, all 300 scores unchanged.

Tests:

- `tests/search.rs::last_two_squares` (new). 10,002 positions with two
  empty squares from `nearly_full(2)`; for the full window `solve`
  must return the exhaustive reference value; for `(v−1, v)`,
  `(v, v+1)` and `(−100, 100)` the result must be a true upper bound
  when at or below alpha, a true lower bound when at or above beta,
  and the exact value otherwise; and `ctx.nodes` must be 1 in every
  case. **Fails today** on the node count ("left: 2, right: 1"); with
  that assertion removed the rest passes on the current engine.
  Cases: mover plays 7,097, mover passes and the opponent plays 1,680,
  nobody can play 1,225; more than 300 of each required.
- `nearly_full(empties)` replaces `one_empty()` (the approved helper,

- Unchanged and binding: as for step 1, plus `last_square` itself.
- Expected in GREEN: `golden_v2`'s node column for the exact rows

## Step 2 GREEN: the last two empty squares

Review of `2df75ae` approved the step 2 test.

What changed (`src/search.rs`):

- `last_two(board, alpha, beta) -> i32` (new, private). An inner
  closure `best(board, beta)` goes through the two empty squares in
  square order; for each one that flips something for that side it
  builds the child board from the flips already computed and takes
  `-last_square(child)`, keeps the maximum, and stops when the value,
  as centidiscs, reaches `beta`. It returns `None` if that side can
  play neither square. `last_two` returns the mover's `best`; if there
  is none, minus the opponent's `best` with the window turned round
  (`-alpha` as its beta); if neither side can play, `final_score` of
  the board. Values are WTHOR discs, converted by the caller like
  `last_square`'s.
- `negamax`: the step 1 check becomes a `match` on
  `(exact, empty_count(board))`: 1 → `last_square`, 2 → `last_two`
  with the node's window. As before this is after the node count and
  stop check and before move generation, the key, the table and the
  move loop; the path's only calls are `flips`, `final_score`,
  `squares` (bit iteration over the two empties), `pass` and
  `last_square`. `root` unchanged.
- Engine lines 1,073 → 1,099 (+26). The two routines together are 43
  lines; the working budget of 1,150 has 51 left.

Tests:

- `last_two_squares` passes (10,002 positions × 4 windows, one node

- Mutations: with the passing side given `-beta` instead of `-alpha`,

## Step 3 RED: no table below 4 empties in exact search

Review of `62084ef` approved step 2.

Intended change: an exact node with fewer than a set number of empties
computes no position key and neither probes nor stores the table. With
steps 1 and 2 in place, nodes with one or two empties already bypass
the table, so the smallest setting that changes anything is 4 (it
takes the table away from nodes with three empties).

Choosing the number. Scratch builds of the step 2 engine with the
cut-off at 3 to 7, `exact_bench`, read off the terminal and not kept as
logs, so this is a pilot and not evidence for the gate:

| Table from … empties | 14-empties nodes | 16-empties nodes | Pilot times against step 2 |
|---|---|---|---|
| 3 (step 2, no change) | 16,535,540 | 51,659,663 | — |
| 4 | 17,212,338 | 53,778,697 | faster in each of four rotations, 16 empties by 1.05 to 1.06 |
| 5 | 18,487,442 | 57,961,617 | about the same as 4, less consistent |
| 6 | 20,262,023 | 63,330,181 | no faster than step 2 |
| 7 | 22,583,689 | 70,385,702 | slower |

All 300 scores identical at every setting. The node counts are exact;
the timing column is deliberately vague because a virtual machine of
the user's was using seven cores during most of those runs (load 8 to
9). I take 4: the smallest change, fewest extra nodes, and at least as
good as 5 in every rotation. Expected gain about 5%, so this step may
land on either side of the bar and will be measured properly, on a
quieter machine, before it is kept.

Tests: none new. This is a cost change inside exact search whose only
observable effects are node counts and time. Binding and unchanged:
`last_square`, `last_two_squares`, `window_equivalence`, the solver
tests including `solver_reuses_endgame_bounds` (which measures what the
table is worth after a win/draw/loss pass; if it fails with the
cut-off, it comes to review, I do not adjust it), `corpus_depths`,
`golden_v1`, `golden_v2` (tableless, so its node counts must not move
at all in this step), and the 300 `exact_bench` positions.

Ready for review. Implementation and measurement follow approval; the
measurement waits for the machine.
