## Step 1: solve times per position (measurement; no engine change, no test stage)

`tools/examples/solve_times.rs` (new example; not counted in the tools
budget). From each of the 200 games in
`docs/tuning/speed_135_match.journal` it takes the first position with
exactly N empties and a legal move, replaying moves and passes and
tracking the colour to move. Each is solved through `search_tt` with
`endgame_threshold` N and limits of depth 64 and a 30,000 ms budget,
timed from the call to its return (so the win/draw/loss pass, the
full-score pass and the root's fallback evaluation are all inside).
Two conditions per position:

- cold: table cleared, then the solve;
- in game: table cleared, then the same side's previous move (the last
  earlier position with that colour to move and a legal move) searched
  with a 3,000 ms budget as a match worker would, then the solve on the
  same table without clearing.

It asserts that when both solves finish their scores agree, and prints
every position (board, both times, both solved flags, score) and per
condition the mean, 95th and 99th percentiles (nearest rank) and
maximum. Logs: `docs/tuning/solve_times_142_e{16,18,20}.log`, engine
sources of `0fa8d8a`, tools release profile, binary hash in each, load
about 1.4 throughout.

Deviation from the issue text: "in game" is the previous own move,
not every own move from 24 empties down. Reason, from the code: exact
search takes no cutoff from heuristic entries (`endgame_cutoff` reads
only `Domain::Endgame`) and no move hint (`hint` is `None` when
`exact`), so what earlier heuristic searches leave in the table can
only displace entries, and the previous own move is the last of them.
The numbers bear that out (below); a longer in-game history would cost
about 10 minutes per earlier move per empties count.

| Empties | Condition | Mean ms | 95th | 99th | Max | Over 3,000 ms | Over 12,000 ms | Not solved in 30 s |
|---|---|---|---|---|---|---|---|---|
| 16 | cold | 54.8 | 171.7 | 347.7 | 412.5 | 0 | 0 | 0 |
| 16 | in game | 56.1 | 173.1 | 348.8 | 413.2 | 0 | 0 | 0 |
| 18 | cold | 379.3 | 1,301.4 | 1,848.6 | 3,297.1 | 1 | 0 | 0 |
| 18 | in game | 381.3 | 1,285.3 | 1,860.5 | 3,296.9 | 1 | 0 | 0 |
| 20 | cold | 3,706.5 | 10,483.3 | 24,135.6 | 30,000.1 | — | — | 2 |
| 20 | in game | 3,706.0 | 10,511.3 | 24,053.6 | 30,000.0 | 73 | 7 | 2 |

The two unsolved 20-empties positions reached the 30 s cap in both
conditions and are counted at 30,000 ms in the mean, which therefore
understates the true mean.

## Step 3 applied to these numbers

The rule, amended in SKIS #142 at the user's decision before the
20-empties results were summarised: the largest N in {16, 18, 20}
whose in-game mean solve time is at most the move time (3,000 ms) and
whose in-game maximum on the 200 games is under the hard limit
(12,000 ms).

- 16: mean 56 ms, max 413 ms. Passes.
- 18: mean 381 ms, max 3,297 ms. Passes. One of 200 positions takes
  longer than the 3,000 ms move time, which the amended rule allows.
- 20: mean 3,706 ms (more than 3,000), max over 30,000 ms (more than
  12,000). Fails both conditions.

**Candidate: N = 18.** Stated now, before step 2 and before any game.
Under the current engine one game in 200 would play an arbitrary move
at 18; step 2's time limit and fallback are what make 18 usable.

## Step 2: what comes next

RED for the solve time limit and fallback follows review of this step.
Design I intend to propose there, for comment now: in `search_inner`'s
exact branch, first run a heuristic iterative search to a small fixed
depth (to be measured; aiming at a few milliseconds at 18 empties)
whose move becomes the fallback; then run the solve with its deadline
moved to four times the move time from the start of the move. If the
win/draw/loss pass finishes, behaviour is as now. If not, the
heuristic move is returned, unsolved. Where the move time comes from
and how `SearchLimits` carries the hard limit is to be settled in RED;
the node limit is unaffected.

## Step 2 RED: solve time limit and heuristic fallback

Step 1 approved (re-review of `4b17306`).

### Design

All in `search_inner`'s exact branch; the heuristic branch is
untouched.

- One `Instant` at the start of the move. The exact branch's deadline
  is that instant plus `time_ms.saturating_mul(4)` (a constant
  `SOLVE_ALLOWANCE = 4`); if the addition overflows there is no
  deadline, as now for `NO_DEADLINE`. The node limit is unchanged and
  still applies to the whole exact search.
- The win/draw/loss pass and the full-score pass run under that
  deadline, as now.
- If the full-score pass does not finish: the pass's move, status
  `Partial`, depth 0, as now.
- If the win/draw/loss pass does not finish (deadline or node limit):
  instead of `fallback_result` (lowest legal square, static score),
  `search_inner` runs again on the same board and table with
  `SearchLimits::depth(8)` and a copy of the configuration with
  `endgame_threshold: 0`, so it takes the heuristic branch with no
  deadline and no node limit and always completes. Its result is
  returned with status `Partial`, `solved` false, depth 8, and its
  nodes added to the failed solve's.
- The fallback search is run after the failure, not before the solve
  as the issue first said; SKIS #142 is amended accordingly (that
  wording was mine). Run after, it costs nothing when the solve
  finishes, so every finished solve's moves, scores and node counts
  stay exactly as they are; `golden_v2` and `exact_bench` node totals
  remain a regression check.

Status of an exact-branch result after the change:

| Outcome | `status` | `depth` | `solved` |
|---|---|---|---|
| Full solve finished | `Complete` | 0 | true |
| Win/draw/loss pass finished, full-score pass did not | `Partial` | 0 | false |
| Win/draw/loss pass did not finish | `Partial` | 8 | false |

`Fallback` no longer comes out of the exact branch. No new status
variant: `depth` already means "heuristic iteration depth" when not
solved, and a new variant would need handling in every exhaustive
match in tools and the GUI.

Depth 8, from a pilot (scratch build, read off the terminal, not a
gate): a depth-8 heuristic search with a cleared table, on the
journal's positions, took mean 1.7 ms and at most 5.9 ms at 18
empties, mean 2.2 and at most 7.6 ms at 20; depth 10 took up to 29
and 45 ms. Since the fallback runs only after up to 4× the move time
has been spent, depth 8 adds at most a few milliseconds to that move.
GREEN measures it in a committed log.

- `cli.rs` `play` (3,000 ms per engine move) and `bench --time-ms`;

- `engine_worker` (matches);

  before this change and stay as they are.

`SearchLimits::time_ms` gains a doc comment saying exact solves get
four times it.

## Review response: step 2 RED (review of `7e31d37`)

Both major findings accepted.

### Node budget: kept, not bypassed

My design ran an unlimited depth-8 search after any failure of the
win/draw/loss pass, including a failure caused by the node limit, and
the new test demanded exactly that. That changed the node contract for
node-controlled callers. Revised policy:

- The fallback search draws on the same node budget. If the search
  had a node limit and the failed solve has used it up, the result is
  the static fallback, `Fallback`, exactly as today; nothing runs past
  the cap.
- If the budget is not used up (no node limit, or a time limit that
  ran out first), the depth-8 search runs with whatever node budget is
  left (no limit when there was none) and no deadline. Its nodes are
  added to the result. If it completes depth 8 the result is `Partial`
  with depth 8; if the remaining node budget stops it earlier, it
  reports the depth it completed (`Partial`), or `Fallback` if it
  completed none.
- So the fallback applies to time-controlled searches, the case the
  user relaxed, and node-controlled searches keep their bound.

Tests, revised:

- `wdl_cancellation_falls_back` is restored unchanged (node limit 1,
  `Fallback`), as the node-budget guard for the endgame. It passes
  today and must still pass.
- `exact_timeout_plays_heuristic` now triggers the fallback with an
  expired time limit (`time_ms: 0`, no node limit) instead of a node
  limit. Positions: 40 sampled with 14 empties, threshold 14, keeping
  only those whose win/draw/loss pass alone needs at least 4,096 nodes
  (the deadline is checked every 1,024 nodes, so a smaller solve can
  finish before the deadline is seen); at least 10 must qualify. The
  assertions are as before: `Partial`, not solved, depth 8, score

### The fourfold allowance is now tested

### What changed

### Cost of the fallback (`docs/tuning/fallback_cost_142.log`)

`tools/examples/fallback_cost.rs` (new example): each journal position

precisely where; it does not measure the boundary, and the factor and
origin are to be checked in the code (`search_inner`, two lines). The
plan's usual smoke tolerance, max(50 ms, 10%), would also cover the
sample maxima.
