# 134: Choose the engine's release profile by measurement

Branch `134-choose-the-engines-release-profile-by-measurement` from
`main` at `edfb56c`, in the main checkout. Build configuration only:
no test stage, no engine source change.

## Summary

- The finding that opened this issue has reversed. In #133, fat
  link-time optimisation was 5 to 10% slower on the midgame workload.
  On the current engine it is about 4% faster.
- The engine's own profile (`lto = "fat"`, `codegen-units = 1`) is
  therefore left as it is.
- The tools crate, which every benchmark, match and gate is built
  from, had no release profile and so measured a build about 4% slower
  than the one that ships. It now carries the same profile, and
  `docs/PLAN.md` records the rule. This is the one change.

## 2. The cause, in the linked binaries

Symbols of the engine left as separate functions in the two
`search_bench` binaries (`nm`, text section):

- lto off: `board::legal_moves`, `board::runs`, `pattern::features`,
  `pattern::evaluate`, `search::negamax`, `search::ordered_moves`,
  `search::root`, `search::search_inner`, `search::search_tt`,
  `search::wdl_root`, `tt::Table::new`, `tt::Table::clear`.
- lto fat: `board::runs`, `pattern::evaluate`, `search::negamax`,
  `search::ordered_moves`, `search::root`.

Without link-time optimisation the engine is a separate crate from
the benchmark, compiled in 16 units, and `features` stays a call from
`evaluate` (returning a 184-byte array through memory) and
`legal_moves` a call from `negamax` on every node. With it, both are
inlined into their callers. Those are the two hottest call edges in
the profile (`features` under every evaluation, `legal_moves` at every
node), which fits a gain of a few percent on the midgame workload and
none on exact search, where there is no evaluation. That is as far as
this evidence goes: I compared which functions exist, not the
instructions inside them, and I have not shown that these two inlinings
account for the whole difference. Why it was the other way round in
#133 I can only guess at (the row-table `features` of that date
vectorised differently under the two settings, as #133's notes
recorded); the code has changed too much since to test that.

Unchanged. Under the issue's rule a change needs 5% on the midgame

## 4. One profile for tools and engine

Decided: yes, and done.

- `tools/Cargo.toml` gains `[profile.release]` with `lto = "fat"` and
  `codegen-units = 1`, and a comment pointing at the plan.
- `scripts/version_workers.sh` states the same profile on its command
  line for both versions (older commits have no profile in
  `tools/Cargo.toml`), in place of the old default it used to pin.
  `tools/tests/version_match.sh` passes with it.
- `docs/PLAN.md` § Build profile (new, under Phase 2 — Strengthening):
  the rule, the reason, and a warning that timings from before this
  issue used the old tools default and are not comparable with later
  ones without re-measuring both sides.

Effect on the tools build, alternating the old default build and the
build this tree now produces, `bench v2`
(`docs/tuning/profile_134_tools_paired_{off16,tools-new}_{1..4}.log`);
pairs 3 and 4 have both runs within 3% on both workloads:

| Pair | Midgame old → new, min ms | Ratio | Exact old → new |
|---|---|---|---|
| 3 | 802.2 → 769.6 | 1.042 | 375.7 → 373.9 |
| 4 | 798.4 → 774.0 | 1.032 | 374.6 → 373.2 |

About 1.03 to 1.04: under 5%, so this is not a speed step that passes
a gate, and I do not present it as one. It is kept for the reason in
the issue's item 4, that benchmarks should measure what ships; the few
percent come with it. Search results are identical (node totals above;
`golden_v2` and the rest of the suite pass under the new profile).

Costs: tools release builds do whole-program optimisation, so a clean
build of an example takes a few seconds longer; nothing else.

Consequence to keep in mind: every tools timing recorded before this
commit (all of #133 to #139) was taken with the old default. Ratios
within those issues stand, each having had both sides on one profile;
absolute times and any comparison across this commit do not carry over.

## Corrections from the review of `d8e3f12`

- The CLI timer. `othello bench` allocates its table before it starts
  the clock, so the printed elapsed time does not include table set-up,
  as I wrote. What it does include is the first-use set-up of the
  evaluation tables (row table, offsets, decoded weights) and a cold
  search. The paired comparison is unaffected.
- Rounding. "Within 0.5%" was too tight: in rotation 3 fat/16 and
  fat/1 differ by about 0.75% on the midgame, and in rotation 2 the
  default and fat/1 differ by about 0.59% on exact search. Read every
  such statement above as "within about 1%".
