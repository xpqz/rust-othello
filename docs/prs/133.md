## Intended change (step 1 GREEN)

Replace the body of `pattern::features` with row tables:
`ROWS[row][byte]` is a `[u16; 46]` holding what the mover's discs in one
board row add to each instance's base-3 index; the opponent's add twice.
8 × 256 × 46 × 2 bytes = 188 KB, built once in a `LazyLock` from
`instances()`. `features` becomes 16 lookups and 16 array additions,
then adds each instance's offset. Signature, results, asset and trainer
unchanged. No `unsafe`, no intrinsics. The largest index is 3^10 − 1 =
59,048, so `u16` sums cannot overflow.

Then: read the assembly of the row-sum loop; if it is scalar, try small
source changes and keep one only if it is vectorised and measurably
faster. Measure `search_rate` again and report lines added. If the gain
is under 5%, revert.

Expected, from the scratch experiment recorded in the issue: `features`
about five times faster, search roughly 1.5 times.

### Vectorisation: a correction and the result

The issue and my earlier reports said the new loop compiled to scalar
code. That was wrong. I had read the per-crate assembly
(`cargo rustc --lib -- --emit asm`), and with `lto = "fat"` that is
emitted before the link-time pass in which the loop vectoriser runs.
The check that counts is the disassembly of the linked binary
(`objdump -d` on `tools/target/release/examples/search_bench`). There,
`pattern::features` uses NEON (`add.8h` on `q` registers); a standalone
copy of the loop compiled with `rustc -O` vectorises the same way. The
issue text is corrected.

Three source forms were compared in the linked binary, two benchmark
runs each, alternating:

| Form | `add.8h` instructions | Midgame min ms (two runs) |
|---|---|---|
| A: 46 lanes, `iter_mut().zip` (kept) | 12 | 7,335.6, 7,345.7 (and 7,177.5, 7,223.5 in separate runs) |
| B: rows padded to 48 lanes, same loop | 138 | 7,119.8, 7,216.5 |
| D: 48 lanes, `chunks_exact(8)` | 18 | 7,074.8, 7,216.2 |

All three are vectorised. B and D were 2 to 3% faster in the paired
runs, which is inside the 1 to 2% run-to-run variation seen for A
alone, and below the 5% bar. Neither is measurably faster, so the
simplest form is kept.

`legal_moves` and `flips` have no vector arithmetic in the linked
binary either; that part of the earlier finding stands, now checked the
right way. They are step 2.

- **Proposed: time handicap in one binary.** Fixed-depth results are
  identical before and after, so the old engine at 3,000 ms behaves like
  the new engine with less time. The midgame workload ratio since the
  start is 2.462, so the old engine is stood in for by the new engine at

  2.462, so this can overstate the gain a little; solves at 14 empties

### Tooling (examples and scripts only; engine untouched)

- `tools/examples/engine_worker.rs` (51 lines). One engine, one game.
  Reads `go <me> <opp>` (hex bitboards, side to move first) and answers
  with a square. It uses only API that is the same at both commits:
  `search_agent(SearchConfig::standard(), SearchLimits::new(64, ms, 0))`.
  A reader thread exits the process the moment stdin closes, even in
  the middle of a search, so a killed driver leaves no worker.
- `tools/examples/version_match.rs` (343 lines). Plays paired games
  between two worker programs: for each opening, one game with A black
  and one with B black. The driver keeps the board, applies passes
  itself and rejects any illegal reply. One journal record per game
  (`pair:game`); a pair finished above the load limit is not recorded
  and is replayed; an interrupted pair is discarded on resume. The
  header holds both worker paths and SHA-256 hashes, time, pairs,
  openings and hash, jobs, load limit and the driver commit, so a
  journal made with other programs or settings is refused. Output:
  W/D/L, score with the pair-bootstrap interval (10,000 resamples), and
  the disc mean with its per-pair standard error.
- `scripts/version_workers.sh <commit-a> <commit-b> <out>`. Archives
  each commit's engine and tools sources into `<out>/src-a` and
  `src-b`, copies this commit's worker source into each, builds each
  with `--release --locked`, and writes `provenance.txt` with commits,
  worker hashes, asset hashes, release profiles, worker source hash and
  `rustc` version.
- `tools/tests/version_match.sh`. Worker protocol from the start
  position; a two-pair match; a six-pair match killed with SIGKILL once
  two games are on record and a worker is running, requiring the driver
  and every worker gone within 0.5 s, then resumed to twelve records
  with every pair that was complete before the kill unchanged; and a
  resume with a different `--time`, which must stop with
  `journal header mismatch`. It uses private copies of the worker so
  only its own processes are matched. Result:
  `version match check passed: resumed from 4 of 12 records, no worker left`.

### Search and table policy, the same for both versions

Each side of each game is its own worker process with its own 64 MiB
transposition table, created empty at the start of the game and kept
between that side's moves; no pondering; standard configuration (exact
solve from 14 empties); a 3,000 ms deadline per move measured inside
the worker. This is what the match tool's in-process agents do.
